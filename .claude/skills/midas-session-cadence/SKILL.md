## Session Cadence (RemoteTriggers + Workflows)
- **Weekday session** (RemoteTrigger, `0 20 * * 1-5`): full 10-agent roster + Oracle. Runs Mon-Fri 20:00 UTC. Authors orders, fills, journals, baselines, posts, blog, snapshots, and writes `data/leaderboard/current.json` as the final orchestrator step (Step 9b in the trigger prose).
- **Weekend refresh** (GitHub Action `refresh-leaderboard.yml`, `0 20 * * 6,0`): valuation-only — no agents, no Oracle, no journals, no posts. Calls `step_fetch_market_data → step_update_snapshots → step_build_baselines` then writes `data/leaderboard/current.json` and commits `chore: weekend refresh YYYY-MM-DD`. Replaced the prior weekend RemoteTrigger session on 2026-05-23 — crypto agents preserve weekend exposure via Friday-authored conditional orders that fire through the watcher.
- **Trigger watcher** (GitHub Actions `check-triggers.yml` daily 13:00 UTC full sweep + `check-triggers-crypto.yml` `--crypto-only`, dispatch-only, fired hourly-at-most by the `workers/trigger-gate/` Cloudflare Worker on a hit): fires pending conditional orders, mutates portfolios, and opportunistically refreshes `data/leaderboard/current.json` (wrapped in try/except — derived state, never fatal to the fill). Blackout 19:55-21:00 UTC to avoid commit-races with the weekday session (20:30 → 21:00 on 2026-08-07; → 21:30 on 2026-08-10 and back to 21:00 on 08-11, tracking the session start both times — see Conditional Triggers).
- **Session-watchdog** (GitHub Action `session-watchdog.yml`, Tue–Sat 02:00 UTC): checks that yesterday's `chore: weekday session` commit actually landed on `main`. Catches the 2026-05-08 class of bugs where a sandbox push 403'd and the work never reached main. **Weekday-only by design** (cron `2-6`): the weekend refresh is valuation-only and commits nothing on a no-diff weekend — a legitimate outcome the watchdog can't distinguish from a silent failure, which produced recurring weekend false alarms (the weekend branch was removed 2026-06-14). **On a miss it files a GitHub issue** (`Missing weekday session YYYY-MM-DD`), then still fails the run. The email alone was not a closed loop: on 2026-08-01 the job correctly caught the missing 07-31 session and the alert went unconsumed — the miss was found by hand, by which point the guard that had already flagged it was irrelevant. An issue persists, is visible without going looking, and stays open until resolved. The job is idempotent (no duplicate issue per date) and auto-closes the issue if the session later lands. A `gh` lookup failure is non-fatal and files anyway — a duplicate issue is cheaper than a missed session.
- **The sentiment A/B records which arm it actually ran.** Step 1a (`step_check_sentiment_freshness`) writes one row per session to `data/market/sentiment_arm.jsonl` (committed): `treatment` when `data/market/news/` holds a same-day digest, `degraded-to-control` when it does not, `not-running` on a desk whose roster declares no treatment arm. Never fatal — a missing news feed is not a reason to lose a session. **It exists because the experiment was confounded from its first day:** `fetch-sentiment.yml` was scheduled 19:00 UTC, ahead of the 20:00 session on paper, but all 36 scheduled runs from 2026-06-15 to 2026-08-05 committed between **20:08 and 21:49 UTC** — after every session had realigned — so the treatment agents read the previous day's headlines every time, with nothing in the record saying so. The cron moved to 18:00, then to 09:00 on 2026-08-12, ahead of a later move of the session itself to 11:00 UTC — at 18:00 an 11:00 session would read the previous day's digest and record a degraded arm every day. The timing is no longer the guarantee; the assertion is. Disclosed in the METHODOLOGY changelog (`#sentiment-lag-2026-08-07`), and the A/B window restarts from the first session whose recorded arm is `treatment`. `roster.yaml` ↔ persona-file membership is pinned by `tests/test_sentiment_arm.py`.
- **Live leaderboard artifact.** `data/leaderboard/current.json` is the single source of truth for the homepage live-leaderboard widget. Written by three paths: weekday session (always), weekend refresh (always), watcher fire (opportunistic). Includes `updated_at` and a `trigger` label so the site can show provenance. Per-day output bundles (`data/output/YYYY-MM-DD.json`) remain weekday-only and drive the per-date archive pages. **Since 2026-08-14 rows rank on `vs_benchmark_pp`** — the book's own-currency return minus its benchmark's, FX-free by construction — with `return_pct` (raw EUR) kept as a column, `vs_coinflip_pp` alongside, and `fx_translation_pp` on non-EUR books naming the translation leg; rows without a baseline series rank after measured ones (null-last, mirroring the site's board-sort). The site renders these engine numbers and computes no deltas of its own — its old `return_pct − benchmark` arithmetic embedded the FX leg on USD books, which is the defect the field exists to end (METHODOLOGY `#leaderboard-rerank-2026-08-14`). **Rows also carry `return_local_pct` and `currency`** (added the same day, no published number moved): the book-currency return is the figure both `vs_*` fields are subtractions on, and publishing it closes an exact identity — `(1 + return_pct) = (1 + return_local_pct) × (1 + fx_translation_pp)` — so the board's decomposition is checkable by a reader rather than assertable only by us. It made `yolo-sapiens-usd` legible: +1.09% in EUR, **−1.07% in USD**, the whole apparent gain being the euro's move. `currency` comes from the engine because the site's roster answers `"mixed"` for `world`, which describes its holdings and not the currency its book is kept in. **`scripts/restate_bundles._METRIC_ERA_FIELDS` must list every one of these fields** — they are legs of one arithmetic, so refreshing a subset on a restated bundle publishes numbers that contradict each other; `tests/test_restate_bundles.py` derives the list from what `build_leaderboard_rows` actually emits rather than trusting it.
- **Session-mode pipeline rule.** Agent-running cadences (weekday today, future holiday-aware cadences) call the exact same `step_*` helpers in `scripts/daily_session.py`. The weekend refresh is a different category — a valuation-only refresh, not a session — and composes a strict subset of those helpers. The journal/posts/blog steps belong to sessions only; baselines + snapshots + `current.json` belong to both. `session-integrity.yml` enforces the per-mode integrity contract. **Asymmetry on `current.json`:** for *session* commits it is a non-fatal **warning** (derived, self-healing state — the cloud orchestrator routinely lands it in a follow-up `… — leaderboard` commit, and the watcher/next session reconcile it within minutes; journals + baselines stay hard failures); for *weekend-refresh* commits a missing `current.json` is a **hard failure**, since writing it is that job's entire purpose. This demotion (2026-06-07) ended a recurring per-commit false failure on the intermediate session commit (4× May–Jun 2026).
- **Snapshots are keyed on the market date and are immutable across sessions.** A row in `data/portfolios/<agent>/snapshots.json` is dated by the *market* date its valuation was priced at, never the session date — `engine/baselines.py` dates every benchmark/coin-flip point from the price series (`idx.date()`), so session-dating the agent curve would drift it off its own benchmark. Because a session runs at 20:00 UTC and the OHLCV cron only captures the previous calendar day's close by its 06:00 UTC run, a session routinely prices against a *previous* market date, and the write used to be an upsert on that key — so it silently overwrote a row a previous session had already published (2026-08-03 rewrote the weekend's 08-02 rows; see the METHODOLOGY changelog). Rows therefore also carry `session_date`, and `PortfolioManager.add_snapshot` **replaces a row only when the same session wrote it** — a re-run correcting itself, which is what the idempotency guarantee actually needs. A later session is refused, returns `False`, and the caller warns. Consequence to expect, not to fix: a session whose store has not advanced records **no new point**, and its valuation lands on the next real close. Legacy rows without `session_date` fail closed. Since 2026-08-06 the baseline series share this contract: `engine.baselines.merge_baseline_series` is **append-or-refuse** — an already-published date is kept as-is, and `restate=True` is the sole, deliberate escape hatch. This closes the asymmetry where a revised close moved a benchmark curve retroactively under a frozen agent curve.
- **Cross-currency positions must be converted before summing, on every pricing path.** A book's positions can be denominated in a currency other than its own (e.g. a EUR book holding `PHAG.L` in GBP or `AUDUSD=X` in USD) — summing `shares * price` without converting mis-prices those positions as if the foreign close were already in the book's currency. The same gap was fixed three times in three places. `scripts/daily_session._compute_positions_value` (snapshots) was fixed by `3b26822f3` — **this sentence claimed it "converted correctly from the start", which that commit's own message refutes** ("the fill path has always converted; the valuation path never did, so five live books carried errors from −13.39% to +4.42% of positions value"); the wrong version was written into this file hours after the fix landed. `engine.restatement` did convert from the start. `engine.valuation.portfolio_mtm` (the leaderboard and the drawdown rail) was the third occurrence, fixed by `296d38459` (2026-08-06). All three paths now convert through the same pair of helpers: `engine.quotes.ticker_currency` to resolve a ticker's native currency, `engine.fx.convert` to convert it. (`paper_broker._ticker_currency` survives only as an alias of the former.) `portfolio_mtm` now returns `None` — not a silently understated total — when a held position needs conversion and the rate is unavailable; this propagates through `portfolio_mtm_eur` (whose caller, `engine.leaderboard.build_leaderboard_rows`, already drops any agent it can't value) and `mtm_base_currency` (whose sole caller, `paper_broker._drawdown_pct`, propagates it). **That fallback was `0.0` until W1 on 2026-08-07 and is not any more:** a book that will not value now fails the batch closed with `VALUATION_UNAVAILABLE`. "Can't determine it, don't halt" reads as caution but switches the drawdown rail off precisely when the book is in an unusual state — an unevaluated rail is not a passed rail. `_drawdown_pct` still returns `0.0` for the genuinely-known no-prior-snapshot case.
- **Bundle is cadence-invariant.** `engine.output_bundle.assemble_output_bundle` always emits all 10 agents in `bundle.agents`, regardless of who ran. Non-runners get `commentary=null, trades=[], posts=[]` and their carry-forward portfolio summary. The orchestrator must build `portfolio_summaries` via `scripts.daily_session.build_portfolio_summaries()` (covers all 10 agents on disk), not by filtering on running agents.
- **The session refuses to price against a store that stopped advancing.** `scripts/fetch_market_data.py` raises `StaleMarketDataError` when the newest close among the *equity* benchmarks (`^GSPC`/`URTH`) is more than **4 calendar days** old, and Step 1 of the session aborts on it. Only the equity side is probed: gold and BTC keep advancing through a weekend and through an equity-vendor outage, so a max over all four benchmarks always looks fresh — which is exactly how a dead equity feed stayed invisible while `fetch_ohlcv.py` exited 0 on failure. 4 days is calibrated on the longest *legitimate* gap, and the bound comes from **which market dates can be missing between the newest close and the session reading it — not from the clock order of the collector and the session**: over a Good-Friday or Christmas weekend the cash market's last close is Thursday's, Friday and the weekend produce no bar at all, and the session that follows runs before its own day's close exists, so the newest close it can see is 4 calendar days old with nothing wrong. That reasoning is independent of the collection hour, which is why the 22:30 → 06:00 move on 2026-08-12 did **not** change the threshold. (The earlier wording — "the OHLCV cron runs after the session" — was read as capture order by one reviewer and clock order by another; it is restated rather than adjudicated.) `tests/test_fetch_market_data.py` pins both sides of the threshold plus that holiday fixture. The payload also now carries **`equity_date`** and a `mixed_dates` note: on a weekend or holiday the snapshot is dated on the freshest benchmark (crypto) while equity positions mark at the last equity close. That is a correct mark — `latest_price` reads the last close on-or-before the date — but it used to be unrecorded. **The date itself is deliberately still the max across all benchmarks**: deriving it from equities alone would collide every weekend-refresh row with Friday's session row (`add_snapshot` refuses a date another session published) and silently end weekend valuation points for the crypto books, which is the weekend refresh's entire purpose.
- **Trading session has no outbound HTTP dependency.** Prices and benchmarks are read from the committed `data/market/ohlcv/` store, populated by the `fetch-ohlcv` GitHub Action cron. `scripts/fetch_market_data.py` is store-only by default — `--allow-network` is local-dev-only.
- The journal rewrite step is load-bearing: if a session's commit touches `data/posts/`, `data/blog/`, `data/output/` but NOT `data/agent_memory/*.md`, Step 8 was skipped. Sessions 2026-04-20..22 hit this bug — weekday trigger fixed on 2026-04-22.
- The baselines step is load-bearing for the site's "vs benchmark / vs coin flip" deltas — if a daily commit touches `data/portfolios/` but not `data/baselines/`, Step 9 was skipped. Same diagnosis pattern as the journals. Saturday 2026-04-25's weekend session hit this bug; weekend trigger fixed on 2026-04-26.
- **Universe data is committed, not cached.** Step 9 (baselines) calls `engine/universes/*` resolvers which need ticker lists for sp500/cac40/dax/ftse100/stoxx600. Those lists live in `data/universes/*.json` (committed). The previous design kept them in `data/cache/universes/` (gitignored, 24h TTL) and tried to refresh from Wikipedia on cache miss — Apr 29 sandbox session needed a manual workaround because outbound HTTP is blocked. Refreshes happen out-of-band only.
- **Persona dispatch substrate.** Project-level subagents in `.claude/agents/*.md` are NOT auto-registered as dispatchable `subagent_type` values (neither locally nor in cloud RemoteTrigger sessions — Apr 29 weekday session aborted on this). Every persona-authored output dispatches through `subagent_type="general-purpose"` with the persona body injected by `engine.persona_dispatch.wrap_persona_prompt(agent_id, task_prompt)`. The orchestrator NEVER inline-authors persona content — wrapping is the substitute for the auto-registration we don't have.
- **The narrator gets a narrator-shaped journal prompt.** `step_build_memory_update_prompts` builds the Oracle's session-end prompt with `engine.agent_memory.build_narrator_memory_update_prompt`, NOT the trader template. The trader template's three fact slots are all structurally empty for an agent that holds no book: `trades_today=[]`, a portfolio summary that renders `PORTFOLIO VALUE TODAY: 0.00 EUR`, and `agent_posts.get("the-oracle")` — which can never hit, because Oracle posts live under `bundle["narrator"]["posts"]` and never enter the `agent_posts` map. Fed that, the Oracle's prompt carried zero session facts and only its own prior journal, so it narrated a dark desk and compounded the error daily: a fabricated "blank streak" from Day 79 to Day 85 (2026-07-23..08-03) across sessions that placed 1–27 orders each. Contained by luck, not design — the blog draft was always correct (`build_oracle_prompt` gets the real digest), the Oracle has no `/arena` page, and `step_load_memories(ROSTER)` never feeds its journal back into the blog. **The narrator prompt must be passed `leaderboard` and `oracle_posts`** — they are its only session facts. Post lists accept `PostPayload` or plain dicts (`engine.agent_memory.post_text`); `step_save_content` types them as the former and the prompt builders used to assume the latter, so the same variable could not feed both.
- **Oracle runs on Sonnet, traders on Opus.** Same Apr 29 session: the Oracle dispatch on Opus repeatedly hit the cloud streaming idle timeout (~60s) while the model was still in pre-output thinking. Sonnet starts streaming in 2-10s and is more than capable of the daily narrative voice. Frontmatter `model:` in `.claude/agents/*.md` controls this; only `the-oracle.md` is on `sonnet`. Trade-round dispatches (single-agent reasoning, smaller prompts) stay on Opus. The Oracle prompt is also trimmed at the source (commentary capped at 240 chars/agent, trade reasoning at 100 chars, journal digest at 250 chars/agent) to keep first-token latency low — see `engine/blog.py` and `engine/agent_memory.format_oracle_digest`.
- **Push path with sandbox-branch fallback.** The trigger ends with `step_git_commit_push()`, which tries `git push origin HEAD:main` first. On 2026-05-08 the harness started 403'ing main pushes from cloud sandboxes (Day 20 commit landed only on `claude/happy-goldberg-VlIfz`, manually merged after); the helper now falls back to `git push origin HEAD` and `.github/workflows/auto-merge-session.yml` takes the merge to main. The auto-merge workflow re-runs the `session-integrity` checks before merging — same artifact rules as the on-main guard — and deletes the sandbox branch after success.


## Conditional triggers — the watcher, the crypto gate, the blackout

### Conditional Triggers (extension of Brain/Hands)

Agents may author conditional orders that defer execution until a price condition fires. Authoring (Brain) happens in the normal daily session; execution (Hands) happens in a separate cron worker:

- Agent emits `{"trigger": {"op": ">=", "level": N}, "expires": "YYYY-MM-DD"}` on any trade in their session output.
- `engine/paper_broker.py:fill_day` recognizes the `trigger` field and routes the order to `data/orders/pending/{order_id}.json` instead of filling immediately.
- `.github/workflows/check-triggers.yml` runs `scripts/check_triggers.py` **daily at 13:00 UTC over all pending orders**, and `.github/workflows/check-triggers-crypto.yml` runs it with `--crypto-only` — **dispatch-only since 2026-08-18**, fired by the Cloudflare Worker gate at `workers/trigger-gate/`, which does the hourly evaluation itself (ONE GraphQL read of both pending channels — REST would need a request per file, 77 today, against the free plan's 50-subrequest cap — plus Coinbase spot for the distinct crypto tickers) and `workflow_dispatch`es this workflow **only when a pending crypto trigger is at or near its level**. **The gate may only over-dispatch, never under-dispatch**: its Coinbase spot price is not the ccxt `last` the workflow reads, so `TOLERANCE` (0.5%) widens the band on the loose side only — a false positive costs one ~1-minute run, a false negative delays a fill by a day. It decides nothing about orders: no expiry retirement, no rails, no fills; the dispatched workflow runs the real `check_triggers.py` with everything. Any time the Worker is dead or misconfigured, crypto conditionals evaluate once daily at the 13:00 sweep — the designed degradation, since that sweep evaluates every asset class and owns expiry, and the reason an isolate-level death (no handler code runs, nothing can self-report) is an accepted risk. Alerting is the Worker's own: on any failure it files or comments the `trigger-gate worker failing` issue, then rethrows so the invocation also shows failed in Cloudflare's cron event history. **Its PAT is a dead-man switch** — when the token dies the Worker fails *and* cannot report it, because the failure issue uses the same dead credential, so the renewal date belongs in a calendar. Its JS copies of Python rules (crypto allowlist, expiry comparison, the pending-channel list) are pinned by `tests/test_trigger_gate_parity.py`, which executes `isLive` through node rather than pattern-matching it. The hourly cron it replaced projected ~1,150-1,200 min/month on its own: 23 runs/day, of which 6 of the first 8 measured 58-71s, astride GitHub's round-up-to-the-minute billing edge. `tests/test_ci_guards.TestCryptoWatcherIsDispatchOnly` pins both directions — no cron, and the dispatch trigger the Worker needs. The split that preceded it landed 2026-08-17: the combined workflow ran `*/15` 24/7 on a header comment asserting midas was a public repo with free Actions minutes — it was private from creation until 2026-08-21, and that one workflow burned 923 of the account's 2,000 monthly minutes (46%) to do ~44 minutes of work, 93% of each run being setup. Crypto is the only class whose evaluation changes intraday (live ccxt fetch, 24/7); everything else reads `latest_close_on_or_before` from the OHLCV store that `fetch-ohlcv.yml` refreshes once a day, so an hourly sweep of an equity trigger re-read byte-identical data. **The daily sweep is the sole owner of expiry** — it is date-based, and the crypto pass filters non-crypto orders out in `run()` (never in `_process_channel`) precisely so an hourly pass cannot retire an equity order early. The hourly schedule skips hour 20 only, not 21 — that rule now lives in the Worker's cron rather than GitHub's: hour 20 is inside the blackout for every value `BLACKOUT_END` has ever held, hour 21 is not, and encoding the movable edge in a cron would create a second place to update when the session moves. The watcher evaluates each pending order's trigger against live prices (ccxt for crypto, OHLCV store for equity/FX) and fires through `engine/paper_broker.execute_triggered_order`, which applies the same **order-level** safety rails as market orders (notional cap, universe allowlist, cash/position/shares checks, FX-rate, apply_trade) but **deliberately skips the two batch-level rails — `MAX_ORDERS_PER_DAY` and `DAILY_DRAWDOWN_HALT`**. Rationale: a triggered fire is not a same-day authored order (so the per-day count does not apply), and the drawdown halt lives at the `fill_day` batch level, not inside per-order processing; a fire that a drawdown would have halted still fills, and the agent reacts next session (see `_execute_triggered_order` docstring).
- Cancellations live as a separate channel: `data/orders/cancels/YYYY-MM-DD.jsonl`. Agents emit a `cancels: [{target_order_id, reasoning}]` field alongside their `trades`. The broker processes cancels at the start of `fill_day`, removes the target pending file, and writes a `CANCELLED_BY_AGENT` rejection to inbox.
- The watcher is blacked out 19:55–21:00 UTC to avoid commit-races with the 20:00 UTC daily session. **The blackout end is a function of the session start — move one and move the other, in the same change.** Measured at a 20:00 start: commits 20:09–20:39, merges 20:12–20:45, so the tail runs to start + ~45 min and the end wants ~15 min on top. The session moved to 20:30 UTC on 2026-08-10 (blackout → 21:30) and back to 20:00 on 08-11 (→ 21:00); the constant has now been wrong in both directions, which is why the rule is stated rather than the number. **The end was 20:30 until 2026-08-07 and that was too early**: measured over the 15 most recent sessions, the session commit lands 20:09–20:39 and the auto-merge 20:12–20:45, so two of the last five ran past the cutoff. A fire in the tail is not a lost fire but a lost *session* — the fire commits to main, and the session's own `assert_session_fresh` then sees the ledger move and discards a completed run. 21:00 clears the measured tail; it does not clear everything (2026-07-29 committed at 21:46). A blackout narrows the race; `session_guard` is the correctness mechanism.
- Supported trigger ops (v1): `>=`, `<=`. Expiry is mandatory; orders without `expires` are rejected at the broker with `TRIGGER_NO_EXPIRY`. Expiry is inclusive — an order with `expires=2026-05-17` is `TRIGGER_EXPIRED` on 2026-05-17.
- **Gate C evaluation protocol** (2026-08-07 review, §5.1). Before the Manager's track record is used to gate real money, three things get recorded alongside the result, because none of them can be reconstructed afterwards: **(1)** the commit SHA the evaluation window was scored at — the ledger has been restated and the append-only gate makes future movement disclosed, but a gate scored against an unpinned "current" basis is not reproducible; **(2)** which ledger basis it was scored on, by name (the reconciled post-`reconcile_quote_currency` basis, and whether the raw-`close` restatement had landed); **(3)** that the Manager's decision prompt was rendering currency-labelled position values — it was not until W7.3, and a track record built on ambiguous numbers is not evidence about the allocator. All three go in the METHODOLOGY changelog entry that announces the gate outcome, not in a working note.
- **Manager channel isolation.** The Manager (`the-manager`) is a config-driven `role: allocator` in `roster.yaml`; its isolated sub-channels (`data/orders/manager-pending/`, `data/orders/manager-cancels/`, `data/orders/manager-inbox/`) are derived from its `channels_prefix`. The broker routes Manager trigger orders to `manager-pending` (not the public `pending/`); the watcher fires them into `manager-inbox` (never the public `inbox/`); idempotency is scoped to the order's target inbox. Manager fills stay out of the public `inbox/` and the ranked leaderboard artifact by design; since 2026-07-24 the Manager has a public **unranked** dossier at `/arena/the-manager` (bespoke page + loaders in `site/src/lib/manager.ts` — it is NOT in `roster.ts`/`TRADING_AGENTS` and never enters `current.json`; the reveal is logged in the METHODOLOGY.md changelog, superseding the 2026-06-28 "artifacts remain private" clause).

Same Brain/Hands invariant: safety rails live in the broker (now both at market-fill time and trigger-fire time), not the persona.
