## Market Data Pipeline
- **Source of truth**: `data/market/ohlcv/{SYMBOL}.jsonl` — one row per trading day, committed to git so the sandboxed remote agent can read prices without calling yfinance at runtime.
- **Every read path takes the raw `close`; nothing reads `adj_close`** (2026-08-07, review §5.2/§7.3). `adj_close` stays in the store as vendor data at rest — ingest still writes it, `normalise_store_units` still scales it, `detect_split` still reasons about it — but no valuation, fill, benchmark, coin flip, FX rate or backtest reads it. Two reasons, and the first is the load-bearing one: **the paper broker never credits dividend cash**, so pricing a position on a dividend-*reinvested* series values a return the book demonstrably did not receive; price return on `close` is the only basis consistent with how the desk executes. Second, **Yahoo re-bases `adj_close` across a symbol's whole history after every payout**, which is structurally incompatible with the append-or-refuse contract — the same date would price differently on two different days with no writer responsible. Splits are not a counter-case: Yahoo restates raw `close` itself for a split, and `engine.corporate_actions` adjudicates that store-side. **Eight read paths had each independently chosen the same `adj_close or close` idiom** (`ohlcv_store`, `fx`, `baselines`, three in `market_data`, `resolve_manager_outcomes`, plus `market_data`'s vendor fallback, which additionally downloaded with `auto_adjust=True` — a store-served raw column and a vendor-served total-return column in one frame, the W7.1 units defect one field over). `tests/test_price_basis.py` pins all of them against a fixture whose two fields deliberately differ, **plus a source-level check that no new reader reintroduces the idiom** — the per-reader tests cannot see a reader written tomorrow, which is how this spread to eight sites. `site/src/lib/ohlcv.ts` already read raw `close`, so the Python↔TS basis divergence closed with it. Cost of the change: 861 published rows moved (104 agent snapshots, 757 coin-flip points), disclosed at METHODOLOGY `#close-basis-2026-08-07`.
- **Restating a baseline series requires a changelog anchor too.** `build_all_baselines(restate_series=…, changelog_entry=…)` refuses a non-empty scope without one (`engine.disclosure`). It was the third path that can move a published number and the last one still ungated — `restate_valuations.py` and `restate_bundles.py` got the precondition in W4.4, but a baseline can only be restated from Python, so there was no CLI flag to require. The routine session call passes no scope and is unaffected.
- **Populator**: `.github/workflows/fetch-ohlcv.yml`. **`0 6 * * 2-6` (Tue–Sat 06:00 UTC)**: full universe (**~1 150 tickers** — equities, ETFs, forex, crypto), capturing the *previous* calendar day's closes. **`0 6 * * 0,1` (Sun–Mon 06:00 UTC)**: `--crypto-only` subset (**~35 tickers**), covering the two days no cash market trades. It ran at 22:30/19:30 until 2026-08-12; 22:30 is the one hour where America has settled and Europe has not, so the store collected a European trading day short every night for five weeks — measured absent at 23:24 on D and at 01:41 on D+1, present at 05:20 on D+1. **The mode is selected from `github.event.schedule`, never from the runner's clock** — the step read `date -u +%u` (Mon–Fri full, Sat–Sun crypto-only) for the whole of 2026-08-12 while the crons above said otherwise, so Saturday fired the full cron and ran crypto-only and Friday's equity closes arrived ~66 h late. A clock read cannot express a cron partition at all: a run delayed past midnight flips its own mode. `tests/test_ci_guards.TestFetchOhlcvScheduleSelectsTheMode` pins each cron to its case arm in both directions. **Both ticker figures move with index composition — do not re-type them from memory.** `python scripts/fetch_ohlcv.py --dry-run` prints `Resolved N symbols to fetch.`, and that line is the only authority (1150 and 34 on 2026-08-02). This paragraph said "~600" and "~30" from the project's first weeks until 2026-08-02; the union of `data/universes/*.json` alone is already 1046 distinct tickers, before crypto and forex are added.
- **Reader**: `engine.market_data.MarketDataFetcher` serves from the store first, falls back to yfinance only when the store doesn't cover the range. Same code path works in local dev and in the sandbox.
- **Previous-day capture, and `end` is YESTERDAY — never today** (2026-08-12). `scripts/fetch_ohlcv.py` sets `end = date.today() - 1`, so the newest day it ever asks the vendor for is one that has fully closed on every instrument. Asking for today costs nothing on a cash market (the day has not opened) but Yahoo serves a daily crypto/FX/futures bar the moment the UTC day opens — verified, a same-day `BTC-USD` close comes back at 07:49 UTC — so at 06:00 that row would be ~6 h formed, the 20:00 session would publish it, and `add_snapshot` would freeze it. Under the old 22:30 cron the same row was ~22.5 h formed: wrong more cheaply, not right. **The published crypto/FX mark is now a final close** (disclosed at METHODOLOGY `#complete-bars-2026-08-12`). **Snapshot dating does not move with it**: at 06:00 on day D the store advances to D−1 and the 20:00 session on D publishes a D−1-dated row, exactly what the 22:30 cron on D−1 produced — verified against the live record (the 08-04 session published 08-03, the 08-05 session published 08-04). `tests/test_fetch_ohlcv_branches.test_the_run_never_asks_the_vendor_for_todays_bar` pins it. `engine.ohlcv_ingest.fetch_window_start` skips a symbol only when the store already holds `end` — never when it merely holds `end - 1`. The prior condition (`last >= end - 1 day`) skipped every other run, leaving roughly half of all daily sessions reading a two-market-day-old equity close; fixed 2026-08-06.
- **The 1-day revision window survives the `end = yesterday` change, with a different job.** `append_new_rows` is append-only and keeps only unseen dates, so any bar that was still forming when first written was frozen at its partial value — the defect the window was built for. With `end` at yesterday nothing partial is ever stored, so **the window now catches the vendor revising an already-complete bar**, which is real and measured (futures moved on 13 of 22 shared days, FX on 5 of 23) and covers Yahoo restating raw `close` outright for a corporate action. `engine.ohlcv_ingest.merge_rows(path, df, revise_from=...)` replaces an already-stored row on or after `revise_from`, and `scripts/fetch_ohlcv.py` requests a **1-day revision window for every symbol**. Do not remove it on the reasoning that partial bars are gone — that is only one of the two things it was catching. A store containing an unparseable line degrades to append-only rather than being reordered.
- **Only cash equities and ETFs were final at 22:30 UTC — measured under the 22:30 schedule, kept as calibration, not restated for 06:00.** Measured over each store's 23 most recent bars against live yfinance (2026-08-06, when the cron ran at 22:30): `SPY` and `AAPL` drifted on **0** of them; commodity futures `PL=F`/`GC=F`/`CL=F` on **13 of the 22 shared days each** (worst +3.365%, +2.865%, +2.516%) because the next Globex session had already opened by 22:30 UTC; FX `GBPJPY=X` on **5 of 23** (worst −1.560%, a Friday) and `EURUSD=X` on **5 of 23** but never past ±0.16%, because the rate rolls at 17:00 ET. **These are 22:30-era numbers and the 06:00 schedule has not been re-measured** — the same rule that governs the finality claim below governs restating them. **They are also no longer a claim about what gets stored**: since `end` moved to yesterday (see the Previous-day-capture bullet) every bar the run stores is complete on every instrument, so what these figures now describe is how much a *complete* bar can still be revised by the vendor afterwards — the thing the 1-day window exists to catch. Exact counts are sensitive to the equality tolerance — the worst-drift figures are the robust part. The window is deliberately universal rather than keyed on an instrument taxonomy that would need maintaining as universes grow: for a bar that *was* final, the re-fetch is identical, `merge_rows` finds nothing to replace, and no already-stored row changes value or position — only the day's new bar is added. A genuine revision *does* rewrite the file; what the universal window guarantees is that no untouched row moves or is re-serialized, so the nightly diff stays one or two lines per file. This paragraph originally read "equity and FX bars are final at fetch time" on the strength of a 3-day sample of one equity and the two mildest FX pairs — a control that could not fail. **Do not restate any finality claim without re-measuring it across instrument classes.**
- **Ingest anomaly tripwire (2026-08-07, review W5).** `merge_rows` is the only place in the system holding **both** the old value and the new one for the same date, which makes it the only place a vendor unit flip, a re-denomination or a bad tick can be caught *before* it becomes that evening's fill price. Passing `quarantine=<path>` refuses a **revision** moving a stored close >20% (`REVISION_LIMIT`) or a **new row** >40% from the previous stored close (`NEW_ROW_LIMIT`), writing it to `data/market/quarantine/{SYMBOL}.jsonl` instead of into the store, and `scripts/fetch_ohlcv.py` exits 1 so the workflow files an issue. **Thresholds are calibrated against measured legitimate revisions, not guessed**: futures drift up to +3.37% and FX to −1.56%, so 20% clears them by better than 5× while sitting two orders of magnitude under a 100× units flip. **Deliberately opt-in and OFF during a resweep** — a real corporate action legitimately rewrites hundreds of rows there, and `detect_split` is what adjudicates them; on the nightly 1-day window a wholesale rewrite of history is never legitimate. Quarantine lives *outside* `data/market/ohlcv/` so a refused row can never be one `glob("*.jsonl")` away from becoming a price.
- **The store-unit migration carries a global completion stamp.** `.unit-migrations.json` records per-symbol conversions **and** `completed_at`. Without the stamp, a pence-quoted ticker fetched for the first time *after* 2026-08-07 is ISO at ingest yet absent from `migrated` — and a re-run would have selected it and divided a pounds file by 100. Keyed on the marker rather than file mtime, because a fresh clone resets every mtime and would answer "everything postdates the migration". `tests/test_normalise_store_units.py` covers it; the script previously had no tests at all.
- **The pre-day-one store drift is German-listed equities, not a currency flip** (diagnosed 2026-08-07, review §5.3 — diagnostic only, no repair). The review's leading hypothesis was "vendor currency-of-quote flips (GBp→USD) in old LSE history, because scattered ratios is what that looks like". **That is false, and was checked rather than reasoned about**: across seven LSE tickers (`LLOY.L`, `PHAG.L`, `FCIT.L`, `BP.L`, `HSBA.L`, `VOD.L`, `SHEL.L`) the stored history and what Yahoo serves today agree on **every one of ~2,518 shared pre-day-one rows each — zero drift**. The drift is **exclusively `.DE`**: 11 of 11 sampled German symbols carry it, 0 of 13 sampled non-German ones do (`.AS`, `.MI`, `.SW`, `.HE`, `.PA`, US, crypto, FX all clean). Shape per symbol: ~31 drifted rows out of ~2,533 (1.2%), scattered across dozens of distinct ratios, median within ±1%, spread up to 17%; the count is barely tolerance-sensitive (31 rows at any difference, 26 above 0.5%), so it is a real revision rather than float noise. Consistent with Yahoo revising German venue closes (XETRA vs regional/auction prints) — **no denomination change is involved anywhere**. This generalises what was already known: `detect_split`'s calibration names `SIE.DE`/`ALV.DE`/`BMW.DE` as its three "real drift" symbols, and the property in fact holds for the whole `.DE` set, which is why the transition check must keep refusing that shape. **Not repaired, deliberately.** No published narrative number reads these rows — the earliest date in any `snapshots.json` or `data/baselines/**` row is 2026-04-17, day one, verified rather than assumed. **The backtester does read them**, for user-specified historical windows, so the ~1% is a known property of German constituents in a long backtest, not a hidden one.
- **Yahoo holes are not our bug — but "unrecoverable" needs a window qualifier.** Yahoo intermittently serves a NaN close (European equities) or no row at all for a given day; `build_new_rows` drops rows with no close, and **since 2026-08-12 it logs the drop** (`_warn_dropped_no_close`, shared with `merge_rows`) instead of a bare `continue` — that silence is how the European side of the store ran a trading day behind the US side for five weeks while every run printed a healthy row count and exited green. A gap is not necessarily permanent: **2026-08-05 crypto was reported unrecoverable on 2026-08-06 and then recovered on 2026-08-07 by a full-history `--resweep`** — Yahoo serves the day over a long window but not over a short one, so a short-window miss is a *request-shape* failure, not proof of absence. Before declaring a date lost, retry it with `--resweep`. Genuinely dead symbols look different: `MATIC-USD` and `UNI-USD` have served nothing since 2025-03-24 and 2025-04-17 at any window.
- **A quarantined row is adjudicated against the vendor's own action calendar** (2026-08-17). The tripwire below could refuse a row but nothing could ever accept one, and `resweep-held-tickers` sweeps **held** tickers only — so a universe ticker nobody holds froze indefinitely: MNST sat on its 2026-08-10 close of 91.43 through a 2:1 split, still buyable by four books at twice its price (no rail objects — `paper_broker._reference_price` compares a BUY against the *prior stored close* from the same frozen file, ratio 1.0 by construction, and `latest_price` has no staleness bound), while `fetch-ohlcv` exited 2 on every full-universe run. `scripts/fetch_ohlcv.py` now asks the vendor's calendar about **only the symbols the tripwire actually refused** — 0 requests on a healthy night, 3 on the worst night this month — and `engine.corporate_actions.explain_quarantine` decides. That placement is the design: `yf.download` carries no corporate actions, so a calendar costs one request per symbol and asking up front for ~1,150 symbols is not affordable; `merge_rows` also stays pure and I/O-free. An explained symbol gets a scoped full-history re-merge with the tripwire off — reusing the `--resweep --symbols` path, so there is one rewrite path rather than two — which accepts the new rows **and** any restated back-history as ONE decision. **That is the fix for the `NEW_ROW_LIMIT` (40%) / `REVISION_LIMIT` (20%) asymmetry, and the asymmetry itself is deliberately unchanged**: a real 20% one-day move must not be quarantined, and the looser new-row bound covers a legitimate gap in a thin name. What was missing was knowing the two sides are one event — JMAT.L's store took 08-13 at +32% through the new-row door while the matching restatement of 08-12 was refused, leaving the series straddling two bases. **There is deliberately NO per-row rule about which side of the effective date a refused row must fall on**, and that is a finding: two such rules were written and each was refuted by a real August fixture (JMAT.L's action *postdates* the revision it explains, because a revision is the vendor restating history; BYND's 08-13 **new row** *predates* its 08-14 action, because the vendor had already restated that bar and the store held no row to revise). Whether a bar arrives as a new row or a revision depends on what the store holds; which basis it carries depends on whether the vendor has restated. Those are independent, so all four combinations are legitimate. What discriminates is that every refused row for the symbol agrees on **one** ratio matching the action (10% relative tolerance — measured error was 0.4% on MNST and 1.7% on BYND, and 10% still separates a 2x split from a 100x units flip), that the action is **recent** (`RECENCY_DAYS`, the only sound date constraint), and that **every** refused row is explained — a partially-explained symbol is refused whole, since adjudication triggers a history rewrite and a share-count mutation. Both a calendar entry and a ratio match are required, so a wrong calendar alone can never admit a bad row. **`data/market/corporate_actions.jsonl` is the idempotency ledger and is committed** (staged by both `fetch-ohlcv` and `resweep-held-tickers`; `tests/test_ci_guards.TestAdjudicationLedgerIsCommitted` pins that, after the existing path-resolution guard correctly caught the file being staged before it existed — the same silent-skip trap as `data/market/quarantine/`). It is not bookkeeping: `apply_split` mutates real share counts, both the nightly fetch and the weekly resweep can see one action, and a double application halves a book twice while the cost-basis invariant hides it. An **unreadable** ledger refuses to adjudicate at all rather than degrading to "assume nothing was applied". `CorporateAction` names `shares_ratio` (the vendor's convention, what `apply_split` consumes) and `price_ratio` (its inverse, what a quarantined row records) separately, because feeding the wrong one halves a holding instead of doubling it. **The exit code subtracts only positively-explained rows from the tripwire's own count** — found while building this, when keying the exit on the adjudication result alone let a `MergeResult` reporting `quarantined=1` with no rows attached exit **0**, a refused row turning the run green by being undescribed. **A row counts as explained only once the re-merge actually lands it** (`remerged.appended or remerged.revised`): the calendar explaining a refusal is not proof the store moved, and Yahoo serves a date over one window and not another in both directions — without that gate the store stays frozen, `unadjudicated` drops to zero, and every later night re-refuses the same rows, hits the `already` branch and exits 0 again, making the freeze permanent *and* invisible. **The ledger is shared by BOTH split paths.** `detect_split`'s resweep branch bypassed it entirely at first, which is a live double-apply: an unrestated split is adjudicated from the calendar tonight, the vendor restates history days later, and Monday's resweep finds exactly the drift `detect_split` was built for — shares x4, cost-basis invariant holding on every application so nothing looks wrong. `detect_split` reports no effective date, so `_match_detected_split` gets one from the calendar on the same `ratios_agree` tolerance (two tolerances for one question is how the paths would disagree about whether an action was already applied); a drift-only detection with no calendar entry keeps the old unledgered behaviour and says so. **Both workflows stage `data/portfolios/`**, because both paths can call `apply_split`: `fetch-ohlcv` staged the ledger but not the holdings, so the share correction would have died with the runner while the ledger row claiming it landed on main — after which the key is in `already` forever and the book keeps half its shares against a post-split price. Same class as METHODOLOGY `#lost-fill-2026-05-21`. Every one of these guards was confirmed capable of failing by breaking its mechanism.
- **Corporate actions (stock splits).** Yahoo *sometimes* retroactively rewrites raw `close` (not just `adj_close`) for every pre-split date once a split occurs — and where it does, a store that isn't resweept after a real split keeps a stale pre-split share count against a post-split price, silently mis-valuing the book by the split ratio. **It does not always, and every detector below is dark for the splits where it does not.** Measured 2026-08-17 on two splits resweept in the same sitting: `JMAT.L`'s 3:4 consolidation restated all 2 601 stored rows and `detect_split` fired correctly at 0.7500, while `MNST`'s 2:1 of 2026-08-11 was **still not restated six days on** — the vendor's own series runs 90.36 (08-07) → 45.53 (08-11), with `adj_close` equal to `close` on both sides of the break. Detection compares stored history against a re-fetch, so with no vendor restatement there is no drift to find, no transition to anchor on, and no ratio to return; a resweep of MNST revised 50 rows and reported no split. What the unrestated split produces instead is a >`NEW_ROW_LIMIT` jump that the ingest tripwire quarantines — correctly, since it cannot tell a split from a units flip — which then **freezes that symbol's store until a human adjudicates it**, and `resweep-held-tickers` will not do it because the sweep is scoped to held tickers. The authoritative answer is free and is not consulted anywhere: the chart API returns the action in its own `events.splits` payload (`{'splitRatio': '2:1', date 2026-08-11}` for MNST), which is what a non-inferential adjudicator would read instead of inferring a ratio from drift that may never appear. `engine.corporate_actions.detect_split` compares a symbol's stored history against a freshly re-fetched series and returns a ratio only when the disagreement has a split's *structure*: a transition date exists (rows after it already agree — a wholly-drifted overlap fails closed, because that is also what a GBp/GBP units mismatch looks like), the drift sits before it (at most 2 stray rows after, for bad ticks), and the drifted rows **nearest the transition** share one ratio. Anchoring at the transition rather than taking a statistic over every drifted row is load-bearing: `FCIT.L` carries an isolated bad tick inside its drifted run (ratio 16.0 against 2 531 rows at 4.0) that reads as "scattered" to any all-rows spread statistic. **A lone bad tick is stepped over; a second *body* of drift older than the cluster is refused outright** — that shape is bit-for-bit a **stacked split** (rows before split1 at `split1 × split2`, rows between at `split2`, clean tail), and no single ratio can correct it, since `apply_split` scales every share of the ticker by one factor while the right factor depends on when each position was opened. Ordinary scattered drift (`SIE.DE`/`ALV.DE`/`BMW.DE`, dozens of distinct ratios within a percent or two, spread throughout the history) must never be auto-corrected and is refused on the transition check. **Calibration is all 11 real splits plus the 3 real drift symbols**, pinned as embedded literal fixtures in `tests/test_corporate_actions.py` (never `git show`/network at test time — CI checks out at `fetch-depth: 1`). **`WLN.PA` is a documented known miss** on a full-history overlap: its older 2 524-row body at 0.0968 is not a second split (Yahoo's calendar lists one), but is indistinguishable from one in the data `detect_split` receives — the implied `split1` of 3.871 is no less plausible than Yahoo's own 3.30087/1.0053 ratios, and the *stored* series really does jump by that factor at the boundary. It is still detected under the 90-day window the weekly job uses, where the older body falls outside the range; widening that window past ~100 days would reintroduce the miss. `.github/workflows/resweep-held-tickers.yml` (weekly, cron `10 04 * * 1`; it was `10 05 * * 1` until 2026-08-12, 50 min from the relocated 06:00 fetch — both rewrite overlapping rows in the same store files, so the exposure was a rebase conflict killing the step, not a lost push) is the scheduled trigger: `scripts/fetch_ohlcv.py --resweep-held --history-days 90` resolves its own symbol list from every currently-held ticker (`_collect_holdings()`, ~30 symbols) and re-fetches with the full-window revision `--resweep` uses, since detection needs a genuine historical overlap the nightly 1-day revision window structurally cannot provide. A detected split adjusts every holding agent's `shares`/`avg_cost` immediately via `PortfolioManager.apply_split` (no confirmation step — same "rails in code, not prompts" design as the broker) and prints a loud `[SPLIT ADJUSTED]` line per agent to the workflow log.
- **A mid-day manual run no longer writes a partial bar at all** (2026-08-12). It used to: with the skip corrected, a `workflow_dispatch` or local `fetch_ohlcv.py` run before the close wrote real same-day rows, the revision window corrected them on the next run, but a session reading the store *in between* priced against the partial and snapshots are immutable (see Session Cadence), so that valuation is what got published. With `end` at yesterday the current day is never requested, so an ad-hoc run at any hour stores only complete bars. What an ad-hoc run *can* still do is advance the store to `end` early, which makes the next scheduled run a no-op for those symbols — harmless, and the case the failure-rate denominator explicitly keeps counting.
- **Not to be confused**: `scripts/fetch_market_data.py` writes a single benchmark snapshot (`data/market/today.json`, gitignored) for daily session commentary. Different job.


## `fetch_ohlcv.py` exit codes, the coverage denominator, and staged files

**`fetch_ohlcv.py` exits 1 when more than 10% of the symbols the store ALREADY COVERS return nothing** (`MAX_FAILURE_RATE`, 2026-08-07 W2.5, recalibrated 2026-08-10). It exited 0 on any failure count, so a total vendor outage produced a green run, "No OHLCV changes to commit", and a session pricing a stale store the next evening. A **rate**, not a count: individually dead symbols are normal and permanent, so any absolute floor would fire nightly or never. An empty vendor frame now also prints to stderr, and `merge_rows` **warns** when an unparseable store line disables revision for a symbol — that degradation is permanent for that file and used to be silent — and salvages the broken line's date out of the raw text so `append_new_rows` cannot write a duplicate row for it.

**The denominator is store coverage, and getting that wrong made the guard cause the outage it detects.** Taken over the whole symbol list the threshold was below the steady-state baseline on the day it shipped: **121 failures of 1,150 (10.5%)** on the four runs preceding it, so *every* full-universe run from 2026-08-07 exited 1, the commit step was skipped, and the price store stopped advancing for four days. **118 of those 121 are Refinitiv-style codes in `data/universes/stoxx600.json`** that Yahoo has no route for — `AIRP.PA`, `BNPP.PA`, `CAGR.PA`, `ATCOa.ST`, `AMBU B.CO` where Yahoo wants `AI.PA`, `BNP.PA`, `ACA.PA`, `ATCO-A.ST`, `AMBU-B.CO`. A symbol that has never served a row and has no store file is a **ticker-resolution** failure, not a vendor outage: it is reported on stderr (`WARN: N symbol(s) have never served a row`) and never fails the run, because holding the price store hostage to a bad universe entry is what broke the desk. Against store coverage the same night reads 2 of ~1,030 (0.2%) and a real outage still reads ~100%. **The stoxx600 ticker formats are a real, still-open defect** — a universe-data bug, not this script's. On an empty store the gate cannot measure and returns 0 by design, so a fork's first bootstrap is never failed. `tests/test_fetch_ohlcv_branches.TestUnresolvedSymbolsAreNotAnOutage` pins the exact production proportions, with a control asserting the old denominator would have failed them.

**Both of `fetch_ohlcv.py`'s deliberate non-zero exits mean "commit this, then go red"** (2026-08-10), and they carry **distinct exit codes so the workflow can tell them from a crash**: `EXIT_QUARANTINED = 2`, `EXIT_VENDOR_OUTAGE = 3`, while an unhandled traceback exits 1. The fetch step captures the code and sets a `committable` output; the push step gates on it. Under the old success-only gate the push never ran on either exit — so the quarantine file, the one artifact the W5 tripwire exists to produce (and which `data/market/quarantine/` was added to the push paths specifically to preserve), was discarded with the runner every single time, and the failure-rate exit threw away a whole night's good rows with the bad news. **A bare `!cancelled()` is the wrong fix and was rejected**: it would also commit a store half-written by a crash at symbol 500 of 1,150, and the session that prices it writes ONE immutable snapshot row per book — so some books mark at today and others at yesterday inside the same published snapshot, with `add_snapshot` refusing any later correction. **`resweep-held-tickers` runs the same script and carries the same gate**, and needs it more: its held set is ~39 tickers, all store-covered, so four vendor misses is already over the limit — and by then `_apply_split_to_holders` has persisted a share/cost-basis correction to `portfolio.json` that a skipped commit would discard for a week.

**`data/tickers.json` is staged by `fetch-ohlcv`** (2026-08-10). `save_registry` rewrites it on every run and **no workflow was staging it**, so the nightly refresh was discarded every night — the file had moved three times ever, all by hand. It is currency-resolution layer 2, so a ticker newly added to a universe never acquired an entry; with the layer-3 heuristic now returning `None` for an unenumerated suffix, the agent's order died at the broker with `CURRENCY_UNRESOLVED`, and the fix was being computed and thrown away nightly.

**`attest-ledger` labels its tag from the HEAD commit's UTC date, not the clock** (2026-08-07, W2.7). Scheduled 23:00 UTC, it actually fired at 00:01–01:44 on all eight most recent runs, so `attest/2026-08-06` was cut at 00:03 on 08-06 attesting a ledger whose newest commit was 08-05 23:42 — seven of eight tags labelled a day ahead of what they attest. "Yesterday UTC" would fix the measured pattern and break the first run that lands at 23:5x; the commit date is a property of the thing attested and is right on either side of midnight.

**`sync_core.check()` iterates the full `apply_manifest`, not just `code_manifest`** (2026-08-07, W2.9). `apply` copies `data/ticker_currencies.json`, `data/tickers.json` and the strategy/universe JSON; `check` did not look at them, so the two halves of the mirror contract disagreed about what the mirror contains. Those two ticker maps are currency-resolution layers 1 and 2 — the least-guarded files in the manifest and the most consequential. A test had pinned the gap as intended behaviour ("data is synced but not guarded"); it now asserts the opposite.

**But `check()` has two tiers, because some of those files are rescraped or rewritten on a schedule** (`REGENERATED_DATA_GLOBS`, 2026-08-10). **Eight files are seeded** into core by `apply` and checked for **presence only**: the seven scraped index universes (`sp500`, `nasdaq100`, `dow30`, `cac40`, `dax`, `ftse100`, `stoxx600`) plus `data/tickers.json`. Everything else in the manifest — **only one ticker map, `data/ticker_currencies.json`**, the strategy specs, and the three *alternative* universes — stays byte-identical. **The universe exemption names the seven individually rather than globbing `data/universes/*.json`**, because `congressional`/`insider`/`high-short` are not scraped: they regenerate deterministically from constants in `engine/universes/alternative.py`, which is itself byte-synced to core, so live and core produce identical bytes for them by construction and a stale copy there is a real defect. Byte-equality on the scraped seven is an invariant a weekly cron legitimately breaks: `refresh-universes.yml` (cron `15 03 * * 1`) rewrites them in live and commits, nothing propagates that to core, and `core-drift-guard` (cron `17 6 * * 1`) runs the same morning — it went red on `sp500.json` + `nasdaq100.json` on 2026-08-10 and would have every Monday a universe moved. **Cite the crons, not observed run times**: that Monday the two actually started 04:55 and 08:05 UTC, and writing those down as the schedule is the mistake the scheduler's lateness (typically 40 min to 2 h 45, tail past 5 h) makes inevitable. **`data/tickers.json` joined the presence-only tier on 2026-08-11**, for a harder reason than the weekly universes: `save_registry` rewrites it on *every* `fetch-ohlcv` run — nightly, not weekly — because Yahoo returns unstable name strings (`"Crédit Agricole S.A."` vs `"CREDIT AGRICOLE"`, `"adidas AG"` vs `"adidas AG    N"`). Byte-guarding it would have put `core-drift-guard` permanently red rather than weekly-red — exactly the failure this tier exists to prevent, and the reason it stops here rather than being re-tightened. A guard a scheduled job is guaranteed to trip teaches everyone to ignore it, which is the exact failure `.github/actions/failure-issue` was built to end, reintroduced one layer up. **This does not weaken W2.9**: its principle was that `apply` and `check` must agree about what the mirror contains, so the two halves were brought back into agreement by correcting what `apply` *promises* — a seed, not a mirror — rather than by letting `check` look away. A **missing** seed is still drift. Core ships `refresh_universes.py` and `fetch_ohlcv.py`, so a fork regenerates both itself; index composition and a vendor name registry are not correctness surfaces the way a currency map is.
