# Midas — AI Fund Manager

## Project Overview
Personal AI fund manager that autonomously analyzes markets, makes investment decisions, and manages portfolios. Two execution engines: bt (Python) for deterministic strategies, Claude agents for analytical ones. Public narrative at `midas.revah.paris` (Astro site, Ring 3a). Streamlit dashboard for local exploration. Backtester API on Google Cloud Run.

## Tech Stack
- Python 3.12+, bt (backtesting), yfinance (market data), pandas-ta (indicators)
- Streamlit + Plotly (dashboard), pytest (testing)
- Claude Code agents for analytical trading strategies

English

## Development
```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

**Dependencies are pinned.** `requirements.in` holds the human-editable loose
constraints; `requirements.txt` is the fully-resolved **lockfile** that every
consumer installs (6 GitHub workflows, the backtester Dockerfile, local dev,
the sandbox). Pinning the full transitive closure makes CI reproducible — a
freshly-published wheel can't break a previously-green run without an explicit
lock bump (origin: the 2026-06-28 pandas 3.0.4 segfault that an unpinned `>=`
let in). To add/change a dep: edit `requirements.in`, then regenerate with
`pip-compile --strip-extras -o requirements.txt requirements.in` (or seed from
the `Successfully installed …` line of a green CI run), and commit both files.

## Testing
```bash
pytest -q            # tests/ AND backtester/tests — both are in `testpaths`
cd site && npm test  # the vitest suite; `npm test` is the authority on the count
```

`.github/workflows/tests.yml` runs **two** jobs: `pytest` and `site-tests`.
Neither is path-filtered per job — the site suite reads committed engine
artifacts (the OHLCV store, `data/ticker_currencies.json`, METHODOLOGY.md
anchors), so "site tests only matter when `site/**` changes" is false. Both had
coverage that existed but never executed: the site suite had no CI job at all
(its double-divide regression and the WCAG contrast guard were green by never
running), and `backtester/tests` sat outside `testpaths`. A testpaths entry
matching nothing is skipped silently, which is what lets this same
`pyproject.toml` sync to midas-core, where no `backtester/` exists.

**The jobs are not path-filtered; the workflow is** (`paths-ignore: data/**`),
and that gap has teeth because the site suite *reads* `data/`. A session
commit's only footprint is `data/`, so the one commit class that changes what
the site suite asserts is the one class that never runs it. Until 2026-08-07
`site/tests/cadence.test.ts` pinned exact literals (216 fills / 87 sessions /
58 fill-days / a per-agent map / a fixed `asOf`), so every session that filled
a trade left `main` red — invisibly, until some unrelated PR ran `pull_request`
(which has no path filter) and failed for reasons that had nothing to do with
it. That is what happened to the 08-07 session: `main` sat red on `npm test`
with nothing reporting it. The pins are now **floors**, matching what
`tests/test_rails_live_coverage.py` already did for the same ledger
(`assert len(fills) > 100`). This is not a weaker assertion of the same thing —
it is the right assertion: the ledger only grows, so a *decrease* is the real
failure mode, and it has occurred (the 2026-05-18..23 `commit_and_push`
pathspec bug silently dropped fills for two months). Per-agent floors are kept
alongside the roster-wide one because a session that adds fills to one book
while dropping them from another leaves the total flat. Verified by deleting a
single fill from `world`'s ledger: three tests fire. The pins' original
rationale — "so the prose gets regenerated rather than going stale" — no longer
applies at all: every consumer (`PreRegistrationStatus`, `MethodologyFacts`,
`oss-stats`, the homepage) calls `cadenceStats()` at build time, so no cadence
figure is transcribed anywhere.

**Warnings are errors, with three named third-party exceptions** (`pyproject.toml`
`filterwarnings`, 2026-08-07). The zero-warnings policy was being asserted, not
enforced — 69 warnings had accumulated. `filterwarnings = ["error", …]` means any
warning not on the list fails the suite; the three that are listed are
unfixable from here (starlette's `TestClient` via `fastapi.testclient`,
`pandas_ta` setting the deprecated `mode.copy_on_write` at import, and `bt`'s
own chained assignment inside `get_transactions`). Matching is on the **message,
not the module**, so an entry stops applying if upstream changes its text — a
stale ignore surfaces as a red run rather than as silent over-suppression.
**A hard gate on warnings is normally fragile and is safe here only because
`requirements.txt` is a full lockfile**: a new third-party warning can arrive
only with a deliberate lock bump. It caught a real defect on its first run —
`test_strategy_specs.py` leaked 15 file handles via `json.load(open(path))`.

**Hypothesis settings live in one profile** (`tests/conftest.py`, `midas`):
`max_examples=1000` per the portfolio mandate, and `deadline=None`. The deadline
is wall-clock and several properties touch the filesystem, so under CI load it
produced intermittent `DeadlineExceeded` failures — a red suite caused by a busy
machine, which trains people to re-run rather than read. Runtime is bounded by
`max_examples` instead, a property of the test rather than of the machine.
Per-test `@settings` had already drifted to 200/300/400 before this; write none
and inherit the profile. `tests/test_money_properties.py` covers the four
transforms a euro actually travels through: unit normalisation, FX conversion,
order serde, fees.

**Published data is guarded in CI, not only in application code** (2026-08-07,
review W4). `session-integrity.yml` now runs three data checks on every push to
main, none of which existed as a standing gate before:
- **ledger-integrity** — every filled inbox row has a matching trade (existence).
- **ledger cash-replay** (`tests/test_ledger_cash.py`) — `initial_capital +
  replay(trades) == live cash`, per book. The existence check cannot see a trade
  booked at the *wrong notional*, which is what the quote-currency defect did to
  24 fills: every row present, joined cleanly, €2,057.65 wrong. The arithmetic is
  imported from `scripts/restate_valuations.py`, not reimplemented.
- **baseline freshness** (`scripts/check_session_freshness.py`, 2026-08-07) —
  the `check` job's Step 9 assertion. It used to grep the commit's changed-file
  list for `^data/baselines/`, which is a proxy for the thing it cares about,
  and the two came apart the same day the append-or-refuse contract landed:
  `a4dc9dce2 [restate]` rebuilt every series that morning, so the evening
  session's Step 9 ran against an already-current series, `merge_baseline_series`
  correctly wrote nothing, and both this guard and the inline copy in
  `auto-merge-session` failed a correct session. **The auto-merge one gates the
  merge** — it was inert only because the direct push to main had already
  succeeded. A diff cannot answer "did Step 9 run"; the published state can: a
  genuine skip leaves the baselines *behind* the snapshots (the Apr 25 shape),
  a correct no-op leaves them level, and a restatement may legitimately run
  ahead, so the check is one-sided. Stdlib only, so no runner needs
  `setup-python`. Calibrated by replaying the real `check` step against
  `32038bcf8` — the commit that went red — and against a hand-broken copy of it.
- **append-only** (`scripts/check_append_only.py`) — a dated row in
  `data/portfolios/*/snapshots.json` or `data/baselines/**` that already exists
  at `HEAD^` must be byte-identical at `HEAD`. A session correcting **its own**
  row is allowed (same `session_date`, exactly what `add_snapshot` permits);
  baselines get no such exemption because they have no writer identity. Anything
  else needs `[restate]` in the commit message — the disclosure requirement made
  mechanical, so `git log --grep='\[restate\]'` is a complete list of every time
  the published record moved. Deliberately a post-hoc detector, not a merge gate:
  `auto-merge-session.yml` runs its own inline copy of the artifact rules, so
  this cannot hold a session hostage. Calibrated by replaying it over real
  history, not only fixtures — see `test_backtest_against_real_history`.

**Restatement requires disclosure up front** (`engine/disclosure.py`).
`restate_valuations.py --apply` and `restate_bundles.py --apply` refuse to run
without `--changelog-entry <anchor>`, and verify the anchor resolves to a real
`<a id>` in METHODOLOGY.md. Dry runs are ungated — you cannot write the
disclosure before you know what would move. Origin: the 2026-08-02 ledger
rewrite that moved a book's published return from +3.30% to +0.19% with no
changelog entry, found five days later by an unrelated cross-check. A
precondition, not an audit: an audit tells you afterwards that you forgot.

**Restatement scope is a set, not a bool.** `build_all_baselines(restate_series=…)`
takes `{"coinflip"}`, `{"benchmark"}` or `{"<agent>/<kind>"}`. The bool it
replaced could only say "everything", which on 2026-08-07 moved eight passive
benchmarks that should not have moved (on fresher *prices*, not units) and they
had to be restored by hand.

**One missing-price policy** (`engine.valuation.value_position`). Snapshots used
to fall back to `avg_cost`, the leaderboard valued at **zero**, and restatement
raised — same book, same missing row, three published answers, two of them
numbers. All three now refuse and name the condition in the broker's own
vocabulary (`NO_PRICE_DATA` / `NO_FX_RATE` / `CURRENCY_UNRESOLVED`).

**The daily attestation asserts something now.** `attest-ledger.yml` ran for 55
green days computing a digest and checking nothing about it — a tampered ledger
produced a different hash and a green run. `attest_ledger.py --verify` re-derives
the previous `attest/*` tag's digest from that tag's own tree (via a detached
worktree, so files deleted since are still covered) and fails on divergence.

**Every guard must be able to fail, and must have a consumer** (2026-08-07, W2.10). Two standing rules, both learned the expensive way — the global "a check that has never produced the opposite answer is not evidence" rule applied to *analyses* here for months while the *standing infrastructure* went unaudited, and eleven guards turned out to be dark or vacuous at once.
1. **Before a guard counts as shipped it must have demonstrably failed**: a historical red, a unit test of its own check logic, or a recorded forced-failure drill. A guard with zero lifetime failures and no self-test is unproven infrastructure, not protection. Where a guard cannot run everywhere it matters (`test_ci_guards.TestRegressionCitations` needs git history that CI's `fetch-depth: 1` does not have), say so in its docstring rather than letting the green tick imply coverage it does not have.
2. **A red X is not a consumer.** Anything scheduled routes failure through `.github/actions/failure-issue`, because `core-drift-guard` was red three consecutive Mondays with nobody reading it, and the watchdog correctly caught the 2026-07-31 miss into an inbox nobody opened.

**Scheduled writers push through `.github/actions/push-with-retry`** (2026-08-07, W2.6). `fetch-ohlcv`, `fetch-sentiment`, `refresh-universes` and `resweep-held-tickers` used a bare `git push`, so when two collided the loser's commit died with the runner. Their nominal cron separation guarantees nothing — GitHub's scheduler runs 42 min to 6 h late and never on time. The action stages, commits, and pushes `HEAD:main` with a rebase-and-retry loop, matching what `scripts/refresh_leaderboard._push_with_rebase_retry` and `check_triggers` already did in Python. It rebases rather than merges, so the history that `git log --grep='[restate]'` and `session-integrity` read stays linear. **`resweep-held-tickers` is the one that most needs it**: its commit can carry a `PortfolioManager.apply_split` correction to real holdings, and a lost push discards that for a week.

**It drops pathspecs that match nothing before staging** (2026-08-10). `git status` and `git add` disagree about an absent path: `status` exits 0 and reports nothing for it, `add` exits 128 with `pathspec ... did not match any files`. So the action's "nothing to commit" guard passed and the stage below it died under `set -e`, taking the run with it. `fetch-ohlcv` passes `data/market/quarantine/`, which exists only once the ingest tripwire has actually refused a row — i.e. never on a healthy night — so its 2026-08-08 and 08-09 runs fetched cleanly (`34 symbols, 0 failures`) and threw the result away. It is the only caller with a path that can be absent. The filter keys on **the worktree OR the index**, mirroring exactly when `git add` succeeds, so staging the deletion of a whole tracked directory still works; filtering on `-e` alone would silently skip it.

**`fetch_ohlcv.py` exits 1 when more than 10% of the symbols the store ALREADY COVERS return nothing** (`MAX_FAILURE_RATE`, 2026-08-07 W2.5, recalibrated 2026-08-10). It exited 0 on any failure count, so a total vendor outage produced a green run, "No OHLCV changes to commit", and a session pricing a stale store the next evening. A **rate**, not a count: individually dead symbols are normal and permanent, so any absolute floor would fire nightly or never. An empty vendor frame now also prints to stderr, and `merge_rows` **warns** when an unparseable store line disables revision for a symbol — that degradation is permanent for that file and used to be silent — and salvages the broken line's date out of the raw text so `append_new_rows` cannot write a duplicate row for it.

**The denominator is store coverage, and getting that wrong made the guard cause the outage it detects.** Taken over the whole symbol list the threshold was below the steady-state baseline on the day it shipped: **121 failures of 1,150 (10.5%)** on the four runs preceding it, so *every* full-universe run from 2026-08-07 exited 1, the commit step was skipped, and the price store stopped advancing for four days. **118 of those 121 are Refinitiv-style codes in `data/universes/stoxx600.json`** that Yahoo has no route for — `AIRP.PA`, `BNPP.PA`, `CAGR.PA`, `ATCOa.ST`, `AMBU B.CO` where Yahoo wants `AI.PA`, `BNP.PA`, `ACA.PA`, `ATCO-A.ST`, `AMBU-B.CO`. A symbol that has never served a row and has no store file is a **ticker-resolution** failure, not a vendor outage: it is reported on stderr (`WARN: N symbol(s) have never served a row`) and never fails the run, because holding the price store hostage to a bad universe entry is what broke the desk. Against store coverage the same night reads 2 of ~1,030 (0.2%) and a real outage still reads ~100%. **The stoxx600 ticker formats are a real, still-open defect** — a universe-data bug, not this script's. On an empty store the gate cannot measure and returns 0 by design, so a fork's first bootstrap is never failed. `tests/test_fetch_ohlcv_branches.TestUnresolvedSymbolsAreNotAnOutage` pins the exact production proportions, with a control asserting the old denominator would have failed them.

**Both of `fetch_ohlcv.py`'s deliberate non-zero exits mean "commit this, then go red"** (2026-08-10), and they carry **distinct exit codes so the workflow can tell them from a crash**: `EXIT_QUARANTINED = 2`, `EXIT_VENDOR_OUTAGE = 3`, while an unhandled traceback exits 1. The fetch step captures the code and sets a `committable` output; the push step gates on it. Under the old success-only gate the push never ran on either exit — so the quarantine file, the one artifact the W5 tripwire exists to produce (and which `data/market/quarantine/` was added to the push paths specifically to preserve), was discarded with the runner every single time, and the failure-rate exit threw away a whole night's good rows with the bad news. **A bare `!cancelled()` is the wrong fix and was rejected**: it would also commit a store half-written by a crash at symbol 500 of 1,150, and the session that prices it writes ONE immutable snapshot row per book — so some books mark at today and others at yesterday inside the same published snapshot, with `add_snapshot` refusing any later correction. **`resweep-held-tickers` runs the same script and carries the same gate**, and needs it more: its held set is ~39 tickers, all store-covered, so four vendor misses is already over the limit — and by then `_apply_split_to_holders` has persisted a share/cost-basis correction to `portfolio.json` that a skipped commit would discard for a week.

**`data/tickers.json` is staged by `fetch-ohlcv`** (2026-08-10). `save_registry` rewrites it on every run and **no workflow was staging it**, so the nightly refresh was discarded every night — the file had moved three times ever, all by hand. It is currency-resolution layer 2, so a ticker newly added to a universe never acquired an entry; with the layer-3 heuristic now returning `None` for an unenumerated suffix, the agent's order died at the broker with `CURRENCY_UNRESOLVED`, and the fix was being computed and thrown away nightly.

**`attest-ledger` labels its tag from the HEAD commit's UTC date, not the clock** (2026-08-07, W2.7). Scheduled 23:00 UTC, it actually fired at 00:01–01:44 on all eight most recent runs, so `attest/2026-08-06` was cut at 00:03 on 08-06 attesting a ledger whose newest commit was 08-05 23:42 — seven of eight tags labelled a day ahead of what they attest. "Yesterday UTC" would fix the measured pattern and break the first run that lands at 23:5x; the commit date is a property of the thing attested and is right on either side of midnight.

**`sync_core.check()` iterates the full `apply_manifest`, not just `code_manifest`** (2026-08-07, W2.9). `apply` copies `data/ticker_currencies.json`, `data/tickers.json` and the strategy/universe JSON; `check` did not look at them, so the two halves of the mirror contract disagreed about what the mirror contains. Those two ticker maps are currency-resolution layers 1 and 2 — the least-guarded files in the manifest and the most consequential. A test had pinned the gap as intended behaviour ("data is synced but not guarded"); it now asserts the opposite.

**But `check()` has two tiers, because some of those files are rescraped on a schedule** (`REGENERATED_DATA_GLOBS`, 2026-08-10). The **seven scraped index universes** (`sp500`, `nasdaq100`, `dow30`, `cac40`, `dax`, `ftse100`, `stoxx600`) are **seeded** into core by `apply` and checked for **presence only**; everything else in the manifest — both ticker maps, the strategy specs, and the three *alternative* universes — stays byte-identical. **The exemption names the seven individually rather than globbing `data/universes/*.json`**, because `congressional`/`insider`/`high-short` are not scraped: they regenerate deterministically from constants in `engine/universes/alternative.py`, which is itself byte-synced to core, so live and core produce identical bytes for them by construction and a stale copy there is a real defect. Byte-equality on the scraped seven is an invariant a cron legitimately breaks: `refresh-universes.yml` (cron `15 03 * * 1`) rewrites them in live and commits, nothing propagates that to core, and `core-drift-guard` (cron `17 6 * * 1`) runs the same morning — it went red on `sp500.json` + `nasdaq100.json` on 2026-08-10 and would have every Monday a universe moved. **Cite the crons, not observed run times**: that Monday the two actually started 04:55 and 08:05 UTC, and writing those down as the schedule is the mistake the 42-min-to-6-h scheduler lateness makes inevitable. A guard a scheduled job is guaranteed to trip weekly teaches everyone to ignore it, which is the exact failure `.github/actions/failure-issue` was built to end, reintroduced one layer up. **This does not weaken W2.9**: its principle was that `apply` and `check` must agree about what the mirror contains, so the two halves were brought back into agreement by correcting what `apply` *promises* — a seed, not a mirror — rather than by letting `check` look away. A **missing** seed is still drift. Core ships `refresh_universes.py`, so a fork regenerates its own; index composition is not a correctness surface the way a currency map is.

**Scheduled workflows alert through `.github/actions/failure-issue`.** A red X
plus a failure email is not a closed loop — `core-drift-guard` was red three
consecutive Mondays while the public mirror shipped stale engine code. The
composite action files a GitHub issue on failure, comments on the existing one
instead of filing duplicates (idempotent per *cause*, not per date — a job
failing five days running is one fact), and closes it on the next success.
Wired into `core-drift-guard`, `fetch-ohlcv`, `fetch-sentiment`,
`refresh-universes`, `resweep-held-tickers`, and **`session-integrity`**;
`session-watchdog` keeps its own per-date variant because each missed session is
a separate fact.

`session-integrity` is the one that is not scheduled, and it was added on
2026-08-07 for the same reason the others were: it went red on main that
evening and produced nothing but an X, found only because someone asked an
unrelated question about the merge. Its three jobs read committed data, so
silence there is the most expensive kind. It reports **once, from a trailing
`alert` job** that `needs` the other three — a run where all three fail is
still one fact, and the action is idempotent per cause, not per job. That job's
own `job.status` is always `success` (it only reports), so the outcome is
aggregated from `needs.*.result`; `tests/test_ci_guards.py` asserts the
aggregation and the `needs` list, and all three of those assertions were
confirmed capable of failing by breaking them one at a time.

## Project Structure
- `engine/` — Core trading logic: types, market data, bt adapter, backtest runner
- `engine/orders.py` — Order/Fill types + outbox/inbox JSONL serde (Brain/Hands primitive)
- `engine/paper_broker.py` — Hands side: 19 rejection/cancel reason codes + fill logic + portfolio update. Since 2026-08-07 the broker can refuse an implausible number, not just an ill-formed one: `PRICE_IMPLAUSIBLE` (fill outside [1/5, 5]x the prior close on a BUY / the position's `avg_cost` on a SELL), `TRIGGER_LEVEL_IMPLAUSIBLE` (conditional level outside [0.2, 5.0]x the latest close, refused **at intake** so it never arms), `CURRENCY_UNRESOLVED` (no layer can denominate the ticker) and `VALUATION_UNAVAILABLE` (the book will not value, so its relative rails cannot be evaluated — an unevaluated rail is not a passed rail). The bands are deliberately loose: they target unit/basis errors, which arrive as a factor of 100, not market moves. `tests/test_rails_live_coverage.py` replays the whole committed ledger against them (216 fills, all within 0.91–1.07x) so a tightened band cannot start refusing real trades unnoticed
- `engine/market_data.py` — the fetcher behind the backtester. **Store first, per ticker; yfinance only for what the store cannot cover, and normalised into ISO on the way in** (2026-08-07, W7.1). Both halves of that were broken: the fallback served raw vendor units (`LLOY.L` at 116.60 where the store gives 1.166), and store coverage was all-or-nothing — one missing or short ticker sent the *whole* request to the vendor, so a single thin name changed the units of every other column. `_close_frame` is now the one composition point for `fetch_prices` and `fetch_benchmarks`, which each had their own copy of the same two defects. Since 2026-08-07 it also downloads with `auto_adjust=False` and takes the raw `Close` block, so a vendor-served column and a store-served one share a basis as well as a unit — see the raw-close rule under Market Data Pipeline.
- `engine/quotes.py` — ticker → currency resolution + price reads. Three layers, in order: the `data/ticker_currencies.json` override map, the vendor's own answer captured into `data/tickers.json` by `scripts/fetch_ohlcv.py`, then a suffix heuristic. A suffix cannot answer the question (`LLOY.L` quotes in pence, `PHAG.L` in USD, and a currency pair quotes in its *second* leg). **Since 2026-08-07 the heuristic returns `None` for a suffix it does not enumerate** instead of defaulting to USD — the fourth failure mode of the quote-currency defect, and the one with no symptom, since a wrong currency still prices. `ticker_currency`, `store_quote`, `latest_price` and `normalise_vendor_quote` are therefore all Optional; the broker turns `None` into `CURRENCY_UNRESOLVED`. A bare ticker keeps USD (Yahoo's US-listing convention, not a guess). `tests/test_rails_live_coverage.py` asserts every **held or pending** ticker resolves from layers 1–2 — not the heuristic — while universe tickers need only resolve to something (130 of 1,046 legitimately sit on the suffix table today). **`GBp` is a unit, not a currency**, and since 2026-08-07 **the store is ISO-denominated**: the pence→pounds division happens ONCE, at ingest, in `scripts.fetch_ohlcv._normalise_vendor_units`. `vendor_quote_unit` returns the vendor's raw unit (ingest + registry only), `ticker_currency` the ISO code, `normalise_vendor_quote` converts a *vendor* price, and `store_quote` attaches a currency to a *stored* price without scaling. Read paths must never scale — doing so divides every LSE price by 100 twice. Mirrored on the site in `site/src/lib/ohlcv.ts`. The migration of the 128 pence files already in the store is `scripts/normalise_store_units.py`, guarded by a marker file because a normalised store is indistinguishable by inspection from a pence one
- `engine/corporate_actions.py` — stock-split detection (`detect_split`, keyed on a *transition-anchored* constant ratio in overlapping OHLCV history — see Market Data Pipeline) + `apply_split` (pure share/avg_cost scaling, cost basis invariant); `PortfolioManager.apply_split` is the only writer
- `engine/posts.py` — post types, config-backed PostPayload + prompt builders + save_daily_posts (display names + schedule now driven by `roster.yaml`)
- `engine/blog.py` — Oracle prompt builder + response parser + blog draft saver
- `engine/agent_memory.py` — Ring 2 per-agent journal I/O + digest/excerpt helpers + session-end rewrite prompt
- `engine/persona_dispatch.py` — load `.claude/agents/{id}.md`, strip frontmatter, wrap a task prompt with the persona body so the orchestrator can dispatch via `subagent_type="general-purpose"` (project agents are not auto-registered as dispatchable subagent types)
- `engine/config.py` — `MidasConfig`: single source of truth for paths + roster + safety rails, loaded from `roster.yaml`; `MIDAS_DATA_DIR`-aware (default = repo root)
- `engine/cli.py` — the `midas` CLI entry point
- `roster.yaml` — the cast (agents, voices, schedule, universes, benchmarks, per-agent safety rails) + globals. **Trader rails recalibrated 2026-08-07**: `max_order_notional_pct: 30` (a *percentage of current book value*, which takes precedence over the absolute `max_order_notional` and re-scales as the book moves), `max_orders_per_day: 10`, `daily_drawdown_halt_pct: -15`. They were `1_000_000 / 100 / -95` on €10,000 books — a per-order cap 100x the whole portfolio. The allocator keeps its absolute `500 / 5 / -5`; forks setting only the absolute field are unaffected. the engine and orchestrator are config-driven from this file. Also declares `sentiment_arm: treatment` on the two agents in the pre-registered sentiment A/B — membership used to exist only as prose in the two persona files and in METHODOLOGY.md, so nothing could report which arm a session actually ran. Special roles: `role: narrator` (the Oracle) and `role: allocator` (the Manager) are declared here — the allocator block is opt-in (omit it to run with no allocator; multiple allocators are supported via distinct `channels_prefix` values). Set `MIDAS_DATA_DIR` to redirect all data reads/writes to a different root (e.g. for forks or isolated test runs).
- `engine/selectors/` — bt Algos for entry signals (golden cross, RSI, etc.)
- `engine/managers/` — bt Algos for position management (grid, trailing stop, etc.)
- `engine/universes/` — Universe resolvers (S&P 500, congressional, crypto, etc.). Read from committed `data/universes/*.json` — no network at runtime. Refresh via `scripts/refresh_universes.py` or the weekly `refresh-universes.yml` workflow.
- `scripts/` — CLI entry points for backtesting and daily sessions
- `scripts/session_state.py` — resumable step markers. **Scoped to the session anchor's `base_sha`, not just the UTC date** (2026-08-07): keyed on `(step, date)` alone, an ad-hoc `step_build_baselines()` run by hand at noon marked that night's real session step as done, and the only symptom was a `[SKIP]` line on a cloud sandbox's stdout. A marker written with no anchor cannot satisfy an anchored session and vice versa; a file written before this change carries no base and fails closed. Re-anchoring onto a moved base discards the day's markers deliberately — the steps already run were computed against a ledger that no longer exists. ## Architecture Principle — Brain / Hands

All external-world integrations in Midas follow a **Brain / Hands split**:

- **Brain** — the Claude Code sandbox (daily trigger cron). Reads from disk, authors decisions (trades, posts, journal entries), writes to an outbox on disk. Holds no external credentials.
- **Hands** — separate workers (paper broker for simulation, future real-broker worker for live execution). Read outbox, validate against safety rails, execute, write confirmations to inbox on disk. Pure executors.

First application (Ring 1): trade execution.
- Agents write orders to `data/orders/outbox/YYYY-MM-DD.jsonl`.
- `engine/paper_broker.py` enforces 15 rejection/cancel reason codes (safety checks), fills at end-of-day close from the OHLCV store, writes to `data/orders/inbox/YYYY-MM-DD.jsonl`.
- Fills with `status="filled"` mutate portfolios via `PortfolioManager.apply_trade`; rejections carry a reason code.
- Every fill (filled or rejected) is stamped with `executed_sha` — the git HEAD commit the broker executed against. Tamper-evident provenance: `git checkout <executed_sha>` re-derives the exact outbox order and price store the broker saw. Resolved by `engine.paper_broker._current_commit_sha`, degrades to `null` (omitted from JSONL) outside a git repo. Covers both `fill_day` and watcher trigger-fires.
- Paper fills carry a realistic per-asset-class fee model (`engine/fees.py`, IBIE/Kraken/FX rates). **The equity commission floor is a EUR amount and is converted into the book's currency** (2026-08-07, W7.4) — it was charged as a bare 1.25 on the USD books, ~8% light on every order small enough for the floor to bind. Rates are percentages of an already-converted notional and are not touched; an unavailable FX rate falls back to the unconverted floor rather than raising (bounded to cents, and on the broker path the rate is necessarily present already). An after-tax shadow ledger (`engine/tax_shadow.py` → `data/tax_shadow/`) estimates PFU drag as a reporting signal — it does not alter portfolio cash.

**Safety rails live in the Hands, not agent prompts.** The agent persona is aspirational; the broker is enforcing.

Real-money transition is a broker swap: replace `paper_broker.py` with an `ibie_broker.py` that talks to Interactive Brokers — same outbox/inbox contract, credentials held outside the sandbox. See `~/.claude/plans/2026-04-17-midas-public-experiment-design-v2.md` for the full experiment design.

### Conditional Triggers (extension of Brain/Hands)

Agents may author conditional orders that defer execution until a price condition fires. Authoring (Brain) happens in the normal daily session; execution (Hands) happens in a separate cron worker:

- Agent emits `{"trigger": {"op": ">=", "level": N}, "expires": "YYYY-MM-DD"}` on any trade in their session output.
- `engine/paper_broker.py:fill_day` recognizes the `trigger` field and routes the order to `data/orders/pending/{order_id}.json` instead of filling immediately.
- `.github/workflows/check-triggers.yml` runs `scripts/check_triggers.py` every 15 minutes. The watcher evaluates each pending order's trigger against live prices (ccxt for crypto, OHLCV store for equity/FX) and fires through `engine/paper_broker.execute_triggered_order`, which applies the same **order-level** safety rails as market orders (notional cap, universe allowlist, cash/position/shares checks, FX-rate, apply_trade) but **deliberately skips the two batch-level rails — `MAX_ORDERS_PER_DAY` and `DAILY_DRAWDOWN_HALT`**. Rationale: a triggered fire is not a same-day authored order (so the per-day count does not apply), and the drawdown halt lives at the `fill_day` batch level, not inside per-order processing; a fire that a drawdown would have halted still fills, and the agent reacts next session (see `_execute_triggered_order` docstring).
- Cancellations live as a separate channel: `data/orders/cancels/YYYY-MM-DD.jsonl`. Agents emit a `cancels: [{target_order_id, reasoning}]` field alongside their `trades`. The broker processes cancels at the start of `fill_day`, removes the target pending file, and writes a `CANCELLED_BY_AGENT` rejection to inbox.
- The watcher is blacked out 19:55–21:00 UTC to avoid commit-races with the 20:00 UTC daily session. **The blackout end is a function of the session start — move one and move the other, in the same change.** Measured at a 20:00 start: commits 20:09–20:39, merges 20:12–20:45, so the tail runs to start + ~45 min and the end wants ~15 min on top. The session moved to 20:30 UTC on 2026-08-10 (blackout → 21:30) and back to 20:00 on 08-11 (→ 21:00); the constant has now been wrong in both directions, which is why the rule is stated rather than the number. **The end was 20:30 until 2026-08-07 and that was too early**: measured over the 15 most recent sessions, the session commit lands 20:09–20:39 and the auto-merge 20:12–20:45, so two of the last five ran past the cutoff. A fire in the tail is not a lost fire but a lost *session* — the fire commits to main, and the session's own `assert_session_fresh` then sees the ledger move and discards a completed run. 21:00 clears the measured tail; it does not clear everything (2026-07-29 committed at 21:46). A blackout narrows the race; `session_guard` is the correctness mechanism.
- Supported trigger ops (v1): `>=`, `<=`. Expiry is mandatory; orders without `expires` are rejected at the broker with `TRIGGER_NO_EXPIRY`. Expiry is inclusive — an order with `expires=2026-05-17` is `TRIGGER_EXPIRED` on 2026-05-17.
- **Gate C evaluation protocol** (2026-08-07 review, §5.1). Before the Manager's track record is used to gate real money, three things get recorded alongside the result, because none of them can be reconstructed afterwards: **(1)** the commit SHA the evaluation window was scored at — the ledger has been restated and the append-only gate makes future movement disclosed, but a gate scored against an unpinned "current" basis is not reproducible; **(2)** which ledger basis it was scored on, by name (the reconciled post-`reconcile_quote_currency` basis, and whether the raw-`close` restatement had landed); **(3)** that the Manager's decision prompt was rendering currency-labelled position values — it was not until W7.3, and a track record built on ambiguous numbers is not evidence about the allocator. All three go in the METHODOLOGY changelog entry that announces the gate outcome, not in a working note.
- **Manager channel isolation.** The Manager (`the-manager`) is a config-driven `role: allocator` in `roster.yaml`; its isolated sub-channels (`data/orders/manager-pending/`, `data/orders/manager-cancels/`, `data/orders/manager-inbox/`) are derived from its `channels_prefix`. The broker routes Manager trigger orders to `manager-pending` (not the public `pending/`); the watcher fires them into `manager-inbox` (never the public `inbox/`); idempotency is scoped to the order's target inbox. Manager fills stay out of the public `inbox/` and the ranked leaderboard artifact by design; since 2026-07-24 the Manager has a public **unranked** dossier at `/arena/the-manager` (bespoke page + loaders in `site/src/lib/manager.ts` — it is NOT in `roster.ts`/`TRADING_AGENTS` and never enters `current.json`; the reveal is logged in the METHODOLOGY.md changelog, superseding the 2026-06-28 "artifacts remain private" clause).

Same Brain/Hands invariant: safety rails live in the broker (now both at market-fill time and trigger-fire time), not the persona.

## Project-Specific Rules
- All strategy specs live in `data/strategies/` as JSON files
- Portfolio state is committed (needed by the sandboxed remote agent)
- Query-hash cached price data goes in `data/cache/` (gitignored)
- Every trade must have a `reasoning` field — no silent trades
- **Share comparisons use a 1e-9 epsilon, not `==`** (`engine.portfolio._DUST_SHARES`, matching `engine.restatement`). 32 of the 227 committed trades are fractional, and `0.3 - 0.1 - 0.2` is 5.55e-17, not zero — so exact comparison left phantom dust positions open forever *and* refused an agent selling the full 0.2 it genuinely held. Both sides of that comparison were wrong; the second was found by the test written for the first.
- **A sale may not drive cash negative.** The equity fee has a floor, so a tiny disposal can cost more than it raises; `apply_trade` now refuses, symmetric with the BUY-side insufficient-cash guard. The broker's rails normally prevent this, but restatement and baseline paths call `apply_trade` directly.
- **A malformed line in the inbox raises.** `inbox_order_ids` is the only thing between an order and a second fill; it used to skip unparseable lines silently, reasoning that a corrupt line "cannot retroactively cause a double-fill if the original write succeeded" — which confuses the write succeeding with the record being readable. A corrupt override map or ticker registry still degrades to `{}` (fail-closed: unresolvable tickers are refused at the broker) but now logs an error, because that degradation silently demotes ~1,000 tickers to the suffix heuristic.
- **Long-only, no short selling.** Use inverse ETFs (`bearish-etfs` universe: SH, PSQ, SQQQ, SPXS, etc.) to express bearish views as long positions. True shorts require borrow data we don't have.

## Market Data Pipeline
- **Source of truth**: `data/market/ohlcv/{SYMBOL}.jsonl` — one row per trading day, committed to git so the sandboxed remote agent can read prices without calling yfinance at runtime.
- **Every read path takes the raw `close`; nothing reads `adj_close`** (2026-08-07, review §5.2/§7.3). `adj_close` stays in the store as vendor data at rest — ingest still writes it, `normalise_store_units` still scales it, `detect_split` still reasons about it — but no valuation, fill, benchmark, coin flip, FX rate or backtest reads it. Two reasons, and the first is the load-bearing one: **the paper broker never credits dividend cash**, so pricing a position on a dividend-*reinvested* series values a return the book demonstrably did not receive; price return on `close` is the only basis consistent with how the desk executes. Second, **Yahoo re-bases `adj_close` across a symbol's whole history after every payout**, which is structurally incompatible with the append-or-refuse contract — the same date would price differently on two different days with no writer responsible. Splits are not a counter-case: Yahoo restates raw `close` itself for a split, and `engine.corporate_actions` adjudicates that store-side. **Eight read paths had each independently chosen the same `adj_close or close` idiom** (`ohlcv_store`, `fx`, `baselines`, three in `market_data`, `resolve_manager_outcomes`, plus `market_data`'s vendor fallback, which additionally downloaded with `auto_adjust=True` — a store-served raw column and a vendor-served total-return column in one frame, the W7.1 units defect one field over). `tests/test_price_basis.py` pins all of them against a fixture whose two fields deliberately differ, **plus a source-level check that no new reader reintroduces the idiom** — the per-reader tests cannot see a reader written tomorrow, which is how this spread to eight sites. `site/src/lib/ohlcv.ts` already read raw `close`, so the Python↔TS basis divergence closed with it. Cost of the change: 861 published rows moved (104 agent snapshots, 757 coin-flip points), disclosed at METHODOLOGY `#close-basis-2026-08-07`.
- **Restating a baseline series requires a changelog anchor too.** `build_all_baselines(restate_series=…, changelog_entry=…)` refuses a non-empty scope without one (`engine.disclosure`). It was the third path that can move a published number and the last one still ungated — `restate_valuations.py` and `restate_bundles.py` got the precondition in W4.4, but a baseline can only be restated from Python, so there was no CLI flag to require. The routine session call passes no scope and is unaffected.
- **Populator**: `.github/workflows/fetch-ohlcv.yml`. Weekdays 22:30 UTC: full universe (**~1 150 tickers** — equities, ETFs, forex, crypto), after US market close. Weekends 19:30 UTC: `--crypto-only` subset (**~35 tickers**), **before** the 20:00 UTC trading session so crypto agents read fresh intraday closes. Invokes `scripts/fetch_ohlcv.py`. **Both figures move with index composition — do not re-type them from memory.** `python scripts/fetch_ohlcv.py --dry-run` prints `Resolved N symbols to fetch.`, and that line is the only authority (1150 and 34 on 2026-08-02). This paragraph said "~600" and "~30" from the project's first weeks until 2026-08-02; the union of `data/universes/*.json` alone is already 1046 distinct tickers, before crypto and forex are added.
- **Reader**: `engine.market_data.MarketDataFetcher` serves from the store first, falls back to yfinance only when the store doesn't cover the range. Same code path works in local dev and in the sandbox.
- **Same-day capture.** The cron runs 22:30 UTC, after the US close, so each run fetches the *current* day's bar. `engine.ohlcv_ingest.fetch_window_start` skips a symbol only when the store already holds `end` — never when it merely holds `end - 1`. The prior condition (`last >= end - 1 day`) skipped every other run, leaving roughly half of all daily sessions reading a two-market-day-old equity close; fixed 2026-08-06.
- **Partial bars are revised, not frozen — on every instrument, not just crypto.** `append_new_rows` is append-only and keeps only unseen dates, so any bar that was still forming when first written was frozen at its partial value. `engine.ohlcv_ingest.merge_rows(path, df, revise_from=...)` replaces an already-stored row on or after `revise_from`, and `scripts/fetch_ohlcv.py` requests a **1-day revision window for every symbol**. **Expect a current-day row to change value on the following run — that is the mechanism working.** A store containing an unparseable line degrades to append-only rather than being reordered.
- **Only cash equities and ETFs are final at 22:30 UTC.** Measured over each store's 23 most recent bars against live yfinance (2026-08-06): `SPY` and `AAPL` drifted on **0** of them; commodity futures `PL=F`/`GC=F`/`CL=F` on **13 of the 22 shared days each** (worst +3.365%, +2.865%, +2.516%) because the next Globex session has already opened by 22:30 UTC; FX `GBPJPY=X` on **5 of 23** (worst −1.560%, a Friday) and `EURUSD=X` on **5 of 23** but never past ±0.16%, because the rate rolls at 17:00 ET. Exact counts are sensitive to the equality tolerance — the worst-drift figures are the robust part. The window is deliberately universal rather than keyed on an instrument taxonomy that would need maintaining as universes grow: for a bar that *was* final, the re-fetch is identical, `merge_rows` finds nothing to replace, and no already-stored row changes value or position — only the day's new bar is added. A genuine revision *does* rewrite the file; what the universal window guarantees is that no untouched row moves or is re-serialized, so the nightly diff stays one or two lines per file. This paragraph originally read "equity and FX bars are final at fetch time" on the strength of a 3-day sample of one equity and the two mildest FX pairs — a control that could not fail. **Do not restate any finality claim without re-measuring it across instrument classes.**
- **Ingest anomaly tripwire (2026-08-07, review W5).** `merge_rows` is the only place in the system holding **both** the old value and the new one for the same date, which makes it the only place a vendor unit flip, a re-denomination or a bad tick can be caught *before* it becomes that evening's fill price. Passing `quarantine=<path>` refuses a **revision** moving a stored close >20% (`REVISION_LIMIT`) or a **new row** >40% from the previous stored close (`NEW_ROW_LIMIT`), writing it to `data/market/quarantine/{SYMBOL}.jsonl` instead of into the store, and `scripts/fetch_ohlcv.py` exits 1 so the workflow files an issue. **Thresholds are calibrated against measured legitimate revisions, not guessed**: futures drift up to +3.37% and FX to −1.56%, so 20% clears them by better than 5× while sitting two orders of magnitude under a 100× units flip. **Deliberately opt-in and OFF during a resweep** — a real corporate action legitimately rewrites hundreds of rows there, and `detect_split` is what adjudicates them; on the nightly 1-day window a wholesale rewrite of history is never legitimate. Quarantine lives *outside* `data/market/ohlcv/` so a refused row can never be one `glob("*.jsonl")` away from becoming a price.
- **The store-unit migration carries a global completion stamp.** `.unit-migrations.json` records per-symbol conversions **and** `completed_at`. Without the stamp, a pence-quoted ticker fetched for the first time *after* 2026-08-07 is ISO at ingest yet absent from `migrated` — and a re-run would have selected it and divided a pounds file by 100. Keyed on the marker rather than file mtime, because a fresh clone resets every mtime and would answer "everything postdates the migration". `tests/test_normalise_store_units.py` covers it; the script previously had no tests at all.
- **The pre-day-one store drift is German-listed equities, not a currency flip** (diagnosed 2026-08-07, review §5.3 — diagnostic only, no repair). The review's leading hypothesis was "vendor currency-of-quote flips (GBp→USD) in old LSE history, because scattered ratios is what that looks like". **That is false, and was checked rather than reasoned about**: across seven LSE tickers (`LLOY.L`, `PHAG.L`, `FCIT.L`, `BP.L`, `HSBA.L`, `VOD.L`, `SHEL.L`) the stored history and what Yahoo serves today agree on **every one of ~2,518 shared pre-day-one rows each — zero drift**. The drift is **exclusively `.DE`**: 11 of 11 sampled German symbols carry it, 0 of 13 sampled non-German ones do (`.AS`, `.MI`, `.SW`, `.HE`, `.PA`, US, crypto, FX all clean). Shape per symbol: ~31 drifted rows out of ~2,533 (1.2%), scattered across dozens of distinct ratios, median within ±1%, spread up to 17%; the count is barely tolerance-sensitive (31 rows at any difference, 26 above 0.5%), so it is a real revision rather than float noise. Consistent with Yahoo revising German venue closes (XETRA vs regional/auction prints) — **no denomination change is involved anywhere**. This generalises what was already known: `detect_split`'s calibration names `SIE.DE`/`ALV.DE`/`BMW.DE` as its three "real drift" symbols, and the property in fact holds for the whole `.DE` set, which is why the transition check must keep refusing that shape. **Not repaired, deliberately.** No published narrative number reads these rows — the earliest date in any `snapshots.json` or `data/baselines/**` row is 2026-04-17, day one, verified rather than assumed. **The backtester does read them**, for user-specified historical windows, so the ~1% is a known property of German constituents in a long backtest, not a hidden one.
- **Yahoo holes are not our bug — but "unrecoverable" needs a window qualifier.** Yahoo intermittently serves a NaN close (European equities) or no row at all for a given day; `build_new_rows` drops rows with no close. A gap is not necessarily permanent: **2026-08-05 crypto was reported unrecoverable on 2026-08-06 and then recovered on 2026-08-07 by a full-history `--resweep`** — Yahoo serves the day over a long window but not over a short one, so a short-window miss is a *request-shape* failure, not proof of absence. Before declaring a date lost, retry it with `--resweep`. Genuinely dead symbols look different: `MATIC-USD` and `UNI-USD` have served nothing since 2025-03-24 and 2025-04-17 at any window.
- **Corporate actions (stock splits).** Yahoo retroactively rewrites raw `close` (not just `adj_close`) for every pre-split date once a split occurs — so a store that isn't resweept after a real split keeps a stale pre-split share count against a post-split price, silently mis-valuing the book by the split ratio. `engine.corporate_actions.detect_split` compares a symbol's stored history against a freshly re-fetched series and returns a ratio only when the disagreement has a split's *structure*: a transition date exists (rows after it already agree — a wholly-drifted overlap fails closed, because that is also what a GBp/GBP units mismatch looks like), the drift sits before it (at most 2 stray rows after, for bad ticks), and the drifted rows **nearest the transition** share one ratio. Anchoring at the transition rather than taking a statistic over every drifted row is load-bearing: `FCIT.L` carries an isolated bad tick inside its drifted run (ratio 16.0 against 2 531 rows at 4.0) that reads as "scattered" to any all-rows spread statistic. **A lone bad tick is stepped over; a second *body* of drift older than the cluster is refused outright** — that shape is bit-for-bit a **stacked split** (rows before split1 at `split1 × split2`, rows between at `split2`, clean tail), and no single ratio can correct it, since `apply_split` scales every share of the ticker by one factor while the right factor depends on when each position was opened. Ordinary scattered drift (`SIE.DE`/`ALV.DE`/`BMW.DE`, dozens of distinct ratios within a percent or two, spread throughout the history) must never be auto-corrected and is refused on the transition check. **Calibration is all 11 real splits plus the 3 real drift symbols**, pinned as embedded literal fixtures in `tests/test_corporate_actions.py` (never `git show`/network at test time — CI checks out at `fetch-depth: 1`). **`WLN.PA` is a documented known miss** on a full-history overlap: its older 2 524-row body at 0.0968 is not a second split (Yahoo's calendar lists one), but is indistinguishable from one in the data `detect_split` receives — the implied `split1` of 3.871 is no less plausible than Yahoo's own 3.30087/1.0053 ratios, and the *stored* series really does jump by that factor at the boundary. It is still detected under the 90-day window the weekly job uses, where the older body falls outside the range; widening that window past ~100 days would reintroduce the miss. `.github/workflows/resweep-held-tickers.yml` (weekly, Monday 05:10 UTC) is the scheduled trigger: `scripts/fetch_ohlcv.py --resweep-held --history-days 90` resolves its own symbol list from every currently-held ticker (`_collect_holdings()`, ~30 symbols) and re-fetches with the full-window revision `--resweep` uses, since detection needs a genuine historical overlap the nightly 1-day revision window structurally cannot provide. A detected split adjusts every holding agent's `shares`/`avg_cost` immediately via `PortfolioManager.apply_split` (no confirmation step — same "rails in code, not prompts" design as the broker) and prints a loud `[SPLIT ADJUSTED]` line per agent to the workflow log.
- **A mid-day manual run writes a partial bar, but no longer freezes one.** With the skip corrected, a `workflow_dispatch` or local `fetch_ohlcv.py` run before the close writes real same-day rows instead of being skipped, and those rows are partial. The universal revision window corrects them on the next run, so this is no longer permanent damage — but a session reading the store *in between* prices against a partial bar, and snapshots are immutable (see Session Cadence), so that valuation is what gets published. Prefer running ad hoc after the close.
- **Not to be confused**: `scripts/fetch_market_data.py` writes a single benchmark snapshot (`data/market/today.json`, gitignored) for daily session commentary. Different job.

## Session Cadence (RemoteTriggers + Workflows)
- **Weekday session** (RemoteTrigger, `0 20 * * 1-5`): full 10-agent roster + Oracle. Runs Mon-Fri 20:00 UTC. Authors orders, fills, journals, baselines, posts, blog, snapshots, and writes `data/leaderboard/current.json` as the final orchestrator step (Step 9b in the trigger prose).
- **Weekend refresh** (GitHub Action `refresh-leaderboard.yml`, `0 20 * * 6,0`): valuation-only — no agents, no Oracle, no journals, no posts. Calls `step_fetch_market_data → step_update_snapshots → step_build_baselines` then writes `data/leaderboard/current.json` and commits `chore: weekend refresh YYYY-MM-DD`. Replaced the prior weekend RemoteTrigger session on 2026-05-23 — crypto agents preserve weekend exposure via Friday-authored conditional orders that fire through the watcher.
- **Trigger watcher** (GitHub Action `check-triggers.yml`, every 15 min): fires pending conditional orders, mutates portfolios, and opportunistically refreshes `data/leaderboard/current.json` (wrapped in try/except — derived state, never fatal to the fill). Blackout 19:55-21:00 UTC to avoid commit-races with the weekday session (20:30 → 21:00 on 2026-08-07; → 21:30 on 2026-08-10 and back to 21:00 on 08-11, tracking the session start both times — see Conditional Triggers).
- **Session-watchdog** (GitHub Action `session-watchdog.yml`, Tue–Sat 02:00 UTC): checks that yesterday's `chore: weekday session` commit actually landed on `main`. Catches the 2026-05-08 class of bugs where a sandbox push 403'd and the work never reached main. **Weekday-only by design** (cron `2-6`): the weekend refresh is valuation-only and commits nothing on a no-diff weekend — a legitimate outcome the watchdog can't distinguish from a silent failure, which produced recurring weekend false alarms (the weekend branch was removed 2026-06-14). **On a miss it files a GitHub issue** (`Missing weekday session YYYY-MM-DD`), then still fails the run. The email alone was not a closed loop: on 2026-08-01 the job correctly caught the missing 07-31 session and the alert went unconsumed — the miss was found by hand, by which point the guard that had already flagged it was irrelevant. An issue persists, is visible without going looking, and stays open until resolved. The job is idempotent (no duplicate issue per date) and auto-closes the issue if the session later lands. A `gh` lookup failure is non-fatal and files anyway — a duplicate issue is cheaper than a missed session.
- **The sentiment A/B records which arm it actually ran.** Step 1a (`step_check_sentiment_freshness`) writes one row per session to `data/market/sentiment_arm.jsonl` (committed): `treatment` when `data/market/news/` holds a same-day digest, `degraded-to-control` when it does not, `not-running` on a desk whose roster declares no treatment arm. Never fatal — a missing news feed is not a reason to lose a session. **It exists because the experiment was confounded from its first day:** `fetch-sentiment.yml` was scheduled 19:00 UTC, ahead of the 20:00 session on paper, but all 36 scheduled runs from 2026-06-15 to 2026-08-05 committed between **20:08 and 21:49 UTC** — after every session had realigned — so the treatment agents read the previous day's headlines every time, with nothing in the record saying so. The cron moved to 18:00, but the timing is no longer the guarantee; the assertion is. Disclosed in the METHODOLOGY changelog (`#sentiment-lag-2026-08-07`), and the A/B window restarts from the first session whose recorded arm is `treatment`. `roster.yaml` ↔ persona-file membership is pinned by `tests/test_sentiment_arm.py`.
- **Live leaderboard artifact.** `data/leaderboard/current.json` is the single source of truth for the homepage live-leaderboard widget. Written by three paths: weekday session (always), weekend refresh (always), watcher fire (opportunistic). Includes `updated_at` and a `trigger` label so the site can show provenance. Per-day output bundles (`data/output/YYYY-MM-DD.json`) remain weekday-only and drive the per-date archive pages.
- **Session-mode pipeline rule.** Agent-running cadences (weekday today, future holiday-aware cadences) call the exact same `step_*` helpers in `scripts/daily_session.py`. The weekend refresh is a different category — a valuation-only refresh, not a session — and composes a strict subset of those helpers. The journal/posts/blog steps belong to sessions only; baselines + snapshots + `current.json` belong to both. `session-integrity.yml` enforces the per-mode integrity contract. **Asymmetry on `current.json`:** for *session* commits it is a non-fatal **warning** (derived, self-healing state — the cloud orchestrator routinely lands it in a follow-up `… — leaderboard` commit, and the watcher/next session reconcile it within minutes; journals + baselines stay hard failures); for *weekend-refresh* commits a missing `current.json` is a **hard failure**, since writing it is that job's entire purpose. This demotion (2026-06-07) ended a recurring per-commit false failure on the intermediate session commit (4× May–Jun 2026).
- **Snapshots are keyed on the market date and are immutable across sessions.** A row in `data/portfolios/<agent>/snapshots.json` is dated by the *market* date its valuation was priced at, never the session date — `engine/baselines.py` dates every benchmark/coin-flip point from the price series (`idx.date()`), so session-dating the agent curve would drift it off its own benchmark. Because a session runs at 20:00 UTC and the OHLCV cron populates the store at 22:30 UTC, a session routinely prices against a *previous* market date, and the write used to be an upsert on that key — so it silently overwrote a row a previous session had already published (2026-08-03 rewrote the weekend's 08-02 rows; see the METHODOLOGY changelog). Rows therefore also carry `session_date`, and `PortfolioManager.add_snapshot` **replaces a row only when the same session wrote it** — a re-run correcting itself, which is what the idempotency guarantee actually needs. A later session is refused, returns `False`, and the caller warns. Consequence to expect, not to fix: a session whose store has not advanced records **no new point**, and its valuation lands on the next real close. Legacy rows without `session_date` fail closed. Since 2026-08-06 the baseline series share this contract: `engine.baselines.merge_baseline_series` is **append-or-refuse** — an already-published date is kept as-is, and `restate=True` is the sole, deliberate escape hatch. This closes the asymmetry where a revised close moved a benchmark curve retroactively under a frozen agent curve.
- **Cross-currency positions must be converted before summing, on every pricing path.** A book's positions can be denominated in a currency other than its own (e.g. a EUR book holding `PHAG.L` in GBP or `AUDUSD=X` in USD) — summing `shares * price` without converting mis-prices those positions as if the foreign close were already in the book's currency. The same gap was fixed three times in three places. `scripts/daily_session._compute_positions_value` (snapshots) was fixed by `3b26822f3` — **this sentence claimed it "converted correctly from the start", which that commit's own message refutes** ("the fill path has always converted; the valuation path never did, so five live books carried errors from −13.39% to +4.42% of positions value"); the wrong version was written into this file hours after the fix landed. `engine.restatement` did convert from the start. `engine.valuation.portfolio_mtm` (the leaderboard and the drawdown rail) was the third occurrence, fixed by `296d38459` (2026-08-06). All three paths now convert through the same pair of helpers: `engine.quotes.ticker_currency` to resolve a ticker's native currency, `engine.fx.convert` to convert it. (`paper_broker._ticker_currency` survives only as an alias of the former.) `portfolio_mtm` now returns `None` — not a silently understated total — when a held position needs conversion and the rate is unavailable; this propagates through `portfolio_mtm_eur` (whose caller, `engine.leaderboard.build_leaderboard_rows`, already drops any agent it can't value) and `mtm_base_currency` (whose sole caller, `paper_broker._drawdown_pct`, propagates it). **That fallback was `0.0` until W1 on 2026-08-07 and is not any more:** a book that will not value now fails the batch closed with `VALUATION_UNAVAILABLE`. "Can't determine it, don't halt" reads as caution but switches the drawdown rail off precisely when the book is in an unusual state — an unevaluated rail is not a passed rail. `_drawdown_pct` still returns `0.0` for the genuinely-known no-prior-snapshot case.
- **Bundle is cadence-invariant.** `engine.output_bundle.assemble_output_bundle` always emits all 10 agents in `bundle.agents`, regardless of who ran. Non-runners get `commentary=null, trades=[], posts=[]` and their carry-forward portfolio summary. The orchestrator must build `portfolio_summaries` via `scripts.daily_session.build_portfolio_summaries()` (covers all 10 agents on disk), not by filtering on running agents.
- **The session refuses to price against a store that stopped advancing.** `scripts/fetch_market_data.py` raises `StaleMarketDataError` when the newest close among the *equity* benchmarks (`^GSPC`/`URTH`) is more than **4 calendar days** old, and Step 1 of the session aborts on it. Only the equity side is probed: gold and BTC keep advancing through a weekend and through an equity-vendor outage, so a max over all four benchmarks always looks fresh — which is exactly how a dead equity feed stayed invisible while `fetch_ohlcv.py` exited 0 on failure. 4 days is calibrated on the longest *legitimate* gap (a Thursday close read by a Tuesday session over a Good-Friday/Easter-Monday weekend, since the OHLCV cron runs after the session), and `tests/test_fetch_market_data.py` pins both sides of the threshold plus that holiday fixture. The payload also now carries **`equity_date`** and a `mixed_dates` note: on a weekend or holiday the snapshot is dated on the freshest benchmark (crypto) while equity positions mark at the last equity close. That is a correct mark — `latest_price` reads the last close on-or-before the date — but it used to be unrecorded. **The date itself is deliberately still the max across all benchmarks**: deriving it from equities alone would collide every weekend-refresh row with Friday's session row (`add_snapshot` refuses a date another session published) and silently end weekend valuation points for the crypto books, which is the weekend refresh's entire purpose.
- **Trading session has no outbound HTTP dependency.** Prices and benchmarks are read from the committed `data/market/ohlcv/` store, populated by the `fetch-ohlcv` GitHub Action cron. `scripts/fetch_market_data.py` is store-only by default — `--allow-network` is local-dev-only.
- The journal rewrite step is load-bearing: if a session's commit touches `data/posts/`, `data/blog/`, `data/output/` but NOT `data/agent_memory/*.md`, Step 8 was skipped. Sessions 2026-04-20..22 hit this bug — weekday trigger fixed on 2026-04-22.
- The baselines step is load-bearing for the site's "vs benchmark / vs coin flip" deltas — if a daily commit touches `data/portfolios/` but not `data/baselines/`, Step 9 was skipped. Same diagnosis pattern as the journals. Saturday 2026-04-25's weekend session hit this bug; weekend trigger fixed on 2026-04-26.
- **Universe data is committed, not cached.** Step 9 (baselines) calls `engine/universes/*` resolvers which need ticker lists for sp500/cac40/dax/ftse100/stoxx600. Those lists live in `data/universes/*.json` (committed). The previous design kept them in `data/cache/universes/` (gitignored, 24h TTL) and tried to refresh from Wikipedia on cache miss — Apr 29 sandbox session needed a manual workaround because outbound HTTP is blocked. Refreshes happen out-of-band only.
- **Persona dispatch substrate.** Project-level subagents in `.claude/agents/*.md` are NOT auto-registered as dispatchable `subagent_type` values (neither locally nor in cloud RemoteTrigger sessions — Apr 29 weekday session aborted on this). Every persona-authored output dispatches through `subagent_type="general-purpose"` with the persona body injected by `engine.persona_dispatch.wrap_persona_prompt(agent_id, task_prompt)`. The orchestrator NEVER inline-authors persona content — wrapping is the substitute for the auto-registration we don't have.
- **The narrator gets a narrator-shaped journal prompt.** `step_build_memory_update_prompts` builds the Oracle's session-end prompt with `engine.agent_memory.build_narrator_memory_update_prompt`, NOT the trader template. The trader template's three fact slots are all structurally empty for an agent that holds no book: `trades_today=[]`, a portfolio summary that renders `PORTFOLIO VALUE TODAY: 0.00 EUR`, and `agent_posts.get("the-oracle")` — which can never hit, because Oracle posts live under `bundle["narrator"]["posts"]` and never enter the `agent_posts` map. Fed that, the Oracle's prompt carried zero session facts and only its own prior journal, so it narrated a dark desk and compounded the error daily: a fabricated "blank streak" from Day 79 to Day 85 (2026-07-23..08-03) across sessions that placed 1–27 orders each. Contained by luck, not design — the blog draft was always correct (`build_oracle_prompt` gets the real digest), the Oracle has no `/arena` page, and `step_load_memories(ROSTER)` never feeds its journal back into the blog. **The narrator prompt must be passed `leaderboard` and `oracle_posts`** — they are its only session facts. Post lists accept `PostPayload` or plain dicts (`engine.agent_memory.post_text`); `step_save_content` types them as the former and the prompt builders used to assume the latter, so the same variable could not feed both.
- **Oracle runs on Sonnet, traders on Opus.** Same Apr 29 session: the Oracle dispatch on Opus repeatedly hit the cloud streaming idle timeout (~60s) while the model was still in pre-output thinking. Sonnet starts streaming in 2-10s and is more than capable of the daily narrative voice. Frontmatter `model:` in `.claude/agents/*.md` controls this; only `the-oracle.md` is on `sonnet`. Trade-round dispatches (single-agent reasoning, smaller prompts) stay on Opus. The Oracle prompt is also trimmed at the source (commentary capped at 240 chars/agent, trade reasoning at 100 chars, journal digest at 250 chars/agent) to keep first-token latency low — see `engine/blog.py` and `engine/agent_memory.format_oracle_digest`.
- **Push path with sandbox-branch fallback.** The trigger ends with `step_git_commit_push()`, which tries `git push origin HEAD:main` first. On 2026-05-08 the harness started 403'ing main pushes from cloud sandboxes (Day 20 commit landed only on `claude/happy-goldberg-VlIfz`, manually merged after); the helper now falls back to `git push origin HEAD` and `.github/workflows/auto-merge-session.yml` takes the merge to main. The auto-merge workflow re-runs the `session-integrity` checks before merging — same artifact rules as the on-main guard — and deletes the sandbox branch after success.
